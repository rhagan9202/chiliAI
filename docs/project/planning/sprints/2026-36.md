## `api.30` was not a bug

The story's premise — that `workflows.py` returns a cursor counting rows the
caller never received — did not survive investigation. The two adapters
*agree* on what the cursor means; neither pre-filters. The work reduced to
documenting the invariant in comments and adding real-Redis parity coverage
that proves the two stores paginate identically. The story is closed as done
because the verification gap it named was real, but no production defect was
fixed, and nothing shipped to `prod` needed reverting.

Three successive descriptions of the Redis mechanism were written before the
fourth was right. Each was committed and then corrected in place
(`de41c9f9`, `b568b646`). The lesson is cheap to state and was expensive to
learn: a claim about how a store behaves is worth checking against the store
before it is written down as fact, not after.

## Two Criticals caught in task review

Both were introduced by this sprint and neither reached the branch tip.

1. **Task 5 — the legacy fold double-counted.** Migrating pre-per-stage
   documents folded `document.warning_count` into a synthetic `legacy` stage,
   but that total already contained both stages' warnings, so every migrated
   document reported inflated counts forever. Fixed by discarding the legacy
   total at write time rather than folding it (`6cd54a28`).
2. **Task 6 — an unconditional `pytest.fail` would have broken every CI run.**
   Making "no completed score run available to replay" a hard failure rested
   on an unexamined assumption: that reaching that line implies a completed
   score run *should* exist. Nothing establishes that. Collection order puts
   the replay test 4th and the only ingest test 6th, and CI brings up a fresh
   Postgres with no seed step. The line would have failed deterministically on
   a *working* stack — in the very job this sprint exists to get green.

   The suggestion to fail unconditionally originated with the controller, not
   the implementer. It was half-right (not gating behind the flag *is*
   correct, since stack presence is already settled by then), which is what
   made it dangerous. Fixed by making the test drive its own precondition —
   push records, poll `entity_count`, start a score run, poll to `completed` —
   rather than scavenging the table for a run another test might have left
   (`dcd7e42b`).

## Known limitation — carried into 2026-37

**No live-stack verification was performed this sprint.** Neo4j's port 7687 on
this host is held by an unrelated project's container, so `make dev` cannot
bring up a complete chiliAI stack. Every e2e path this sprint touched —
including Task 6's rewritten push → score → replay sequence — is verified
statically (routes, payload shapes, response models, config defaults) and by
the non-stack suite, but has not been executed against a real API and worker.

The CI backend job has still never completed a run. Getting it green is the
first thing to confirm in 2026-37, and it is the whole reason `cicd.22`
existed.
