## Current-state snapshot

- **Plan A done.** `backend/database/` ships `ConnectionProvider`/`DatabaseConnection`/`DatabaseCursor` protocols (`protocols.py:17-53`), a psycopg-pool-backed provider built lazily so the module imports without the `[postgres]` extra (`engine.py:42-99`), `runtime.create_connection_provider(config)` returning `None` for the in-memory backend (`runtime.py:13-32`), a `SELECT 1` readiness probe (`health.py:8-16`), and a typed `DatabaseError` hierarchy (`exceptions.py`).
- **Plan C done.** Per-consumer Postgres adapters exist for every analytics-facing table (`monitoring/adapters/postgres.py` for `observations` + `alert_history`, `analytics/timeseries/adapters/postgres.py`, `analytics/risk/adapters/postgres.py`, `analytics/metrics/adapters/postgres.py`, `records/adapters/postgres.py`) and are wired from both composition roots (`api/dependencies.py:695-720`, `agent/coordinator.py:458-505,667-695`).
- **Schema baseline.** Single Alembic revision `0001_persistence_baseline` (`backend/database/migrations/versions/0001_persistence_baseline.py:18-160`) creates the six tables from spec §6 and converts `observations` and `entity_metric_history` to TimescaleDB hypertables. No second revision exists — every schema change since baseline is still future work.
- **Pool config.** `DatabaseConfig` exposes `pool_size=10`, `pool_max_overflow=5`, `statement_timeout_ms=30000` (`config/schema.py:159-166`); `_configure` applies `statement_timeout` per session-checkout (`engine.py:60-69`). No connection-acquire timeout, no `connect_timeout`, no keepalives, no `application_name`, no read-only/replica role separation, no per-environment pool tuning.
- **Migration runner.** Alembic env reads `DATABASE_URL` from the environment and normalizes the dialect to `postgresql+psycopg://` (`migrations/env.py:19-25`); `target_metadata = None` (raw SQL only). `make migrate` runs `alembic upgrade head` against the dev compose stack (`Makefile:33`); no `alembic check`, no schema-snapshot diff in CI, no "migrations are backward-compatible with running pods" gate.
- **TimescaleDB.** Dev compose uses `timescale/timescaledb:latest-pg16` with `shared_preload_libraries=timescaledb` (`docker-compose.dev.yaml:146-156`); the baseline migration calls `create_hypertable` on two tables but never sets retention, compression, or continuous-aggregate policies — spec §15 explicitly defers this.
- **Plan B not started.** Workflow run state lives in `agent/adapters/redis_store.py` (`RedisWorkflowRunStore`) or in-memory (`agent/adapters/in_memory.py`), selected via `CHILI_WORKFLOW_RUN_STORE_BACKEND={in_memory,redis}` (`agent/adapters/runtime.py:18-29`). There is no Postgres backend for workflow runs, no `workflow_runs` table in any migration, and no follow-up Alembic revision.
- **KB-metadata adapter gap.** `knowledgebases/adapters/` ships only `InMemoryKnowledgeBaseRepository` and `ObjectStoreKnowledgeBaseRepository` (single-writer JSON blob); `architecture.md:1369` flags "Add a production-grade KB metadata adapter/migration path" as an explicit current gap.
- **No tenant_id columns.** Every Plan C table is keyed by `knowledge_base_id` only (`migrations/versions/0001_persistence_baseline.py:31,54,79,98,113,131`); there is no `tenant_id` column and no row-level-security policy. Multi-tenancy will require a schema migration before any tenant work lands.
- **No TLS to DB.** `_normalize_dsn` strips `+psycopg` but does not enforce `sslmode` (`engine.py:36-39`); `docker-compose.dev.yaml:66,106` ships `postgresql://chili:chili@postgres:5432/chili` with no SSL. No `sslrootcert`/`sslmode=verify-full` story for production.
- **No query observability.** Nothing in `database/` enables `pg_stat_statements`, exposes pool metrics (`getconn` wait time, in-use vs idle), logs slow queries, or emits OpenTelemetry spans around `provider.connection()` / cursor execute.
- **No read replicas.** Single pool, single DSN. `ConnectionProvider.connection()` does not distinguish read-only from read-write; analytics-read endpoints (`get_monitoring_observation_source`, timeseries history queries) share the writer pool.
- **No backup/restore plumbing.** `infra/` has no `pg_basebackup` CronJob, WAL archiving, PITR plan, or restore drill — `_infra.md` epic 13 owns the manifest side; schema-level safeguards (e.g. `pg_dump` excludes for blob columns) are unowned today.
- **Schema docs.** No auto-generated ER diagram, no `\dt`-style table inventory, no per-table comments in the migration. The schema reference is the design spec narrative + reading the migration file.

## Provisional epic list

1. **Land a workflow-run Postgres adapter and Plan B migration.** `agent/adapters/runtime.py:18-29` selects only `in_memory` and `redis` today; add a `PostgresWorkflowRunStore` plus an Alembic revision for the `workflow_runs` / `workflow_run_history` / `workflow_run_idempotency` schema implied by `RedisWorkflowRunStore` semantics, and a `CHILI_WORKFLOW_RUN_STORE_BACKEND=postgres` selector. Closes the last "Plan B" gap from `docs/superpowers/specs/2026-05-14-backend-persistence-design.md`.
2. **Add a Postgres knowledge-base metadata adapter.** `knowledgebases/adapters/` ships only `InMemoryKnowledgeBaseRepository` and `ObjectStoreKnowledgeBaseRepository`; `architecture.md:1369` explicitly flags this as a current production-readiness gap. Add `PostgresKnowledgeBaseRepository`, the schema migration (`knowledge_bases`, `documents`, `document_versions`), and wire `CHILI_KB_REPOSITORY_BACKEND=postgres` through `api/dependencies.py:747-759`.
3. **Establish a backward-compatible / zero-downtime migration convention.** Only one revision exists (`0001_persistence_baseline`); there is no documented rule for additive-only DDL, no "expand-then-contract" template, no `pre_deploy`/`post_deploy` revision split. Write the convention into `backend/database/README.md` and gate it with lint rules (forbid `DROP COLUMN`, `ALTER COLUMN TYPE`, `RENAME` in a single revision without an explicit two-phase tag) in the consistency check.
4. **Detect migration drift in CI.** Nothing today asserts that `alembic upgrade head` against the current `main` schema is a no-op for an already-migrated DB, or that no revision was added without a regenerated baseline. Add a CI job that boots a fresh Postgres, runs `alembic upgrade head`, then runs `alembic check` (or a schema-snapshot diff) — fails the PR on drift. (Cross-edge: `_cicd.md`.)
5. **Production-grade connection pool tuning and per-role pools.** `DatabaseConfig` exposes `pool_size=10`/`pool_max_overflow=5` only (`config/schema.py:159-166`); add `connect_timeout`, `keepalives`, `application_name=chili-{api,worker}`, an acquire-timeout, separate reader/writer pools, and per-environment defaults (`medicare_fraud.yaml` vs `medicare_fraud_dev.yaml`). Tune for the worker handler concurrency observed in `agent/coordinator.py`.
6. **Read-replica routing through the `ConnectionProvider`.** Today `ConnectionProvider.connection()` returns a writer connection (`protocols.py:47-53`, `engine.py:93-96`); analytics read paths (`monitoring/adapters/postgres.py`, `analytics/timeseries/adapters/postgres.py`) share the writer pool. Add `read_only` mode to the protocol, a reader pool built from `READ_REPLICA_URL`, and per-call selection in the read-side adapters. (Cross-edge: `_infra.md` for the actual replica.)
7. **Enforce TLS to the database from API and worker.** `engine._normalize_dsn` (`engine.py:36-39`) does not require `sslmode`; dev compose uses unencrypted Postgres. Add `DatabaseConfig.sslmode: Literal["disable","require","verify-full"]`, a `sslrootcert_path` field, and refuse to start in `staging`/`production` when the effective DSN resolves to `sslmode=disable`. (Cross-edge: `_security.md`.)
8. **Add tenant-aware columns and row-level-security to every Plan C table.** Every table in `0001_persistence_baseline` keys on `knowledge_base_id` only (`migrations/versions/0001_persistence_baseline.py:31,54,79,98,113,131`); there is no `tenant_id` and no RLS policy. Land a migration adding `tenant_id text NOT NULL`, backfill from `knowledge_base_id → tenant_id`, add composite PKs/indexes, and enable RLS keyed off a `SET LOCAL chili.tenant_id` per request. (Cross-edge: `_multitenancy.md`.)
9. **TimescaleDB retention, compression, and continuous-aggregate policies.** `0001_persistence_baseline` creates two hypertables (`observations`, `entity_metric_history`) but sets no retention or compression — explicitly deferred in spec §15. Add a follow-up revision with `add_retention_policy` (e.g. 90 d for `observations`, 365 d for `entity_metric_history`), `add_compression_policy` after 7 d, and a `continuous_aggregate` for the daily entity-metric rollup feeding `entity_metrics_current`.
10. **Query observability: pg_stat_statements, slow-query log, pool metrics, DB-span tracing.** Nothing in `database/` enables `pg_stat_statements`, logs slow queries, or instruments `PsycopgConnectionProvider.connection()` (`engine.py:93-96`). Add a compose/`infra` flag turning on the extension, a `log_min_duration_statement` setting, Prometheus exporters for psycopg-pool gauges (in-use, idle, waiting), and OpenTelemetry spans wrapping every `provider.connection()` checkout. (Cross-edge: `_observability.md`.)
11. **Per-table column comments and auto-generated schema docs.** `0001_persistence_baseline` has no `COMMENT ON COLUMN` statements; there is no ER diagram in `docs/`. Add comments inline in the next revision, then a `scripts/dump_schema_docs.py` that runs against a freshly-migrated DB and writes `docs/database/schema.md` + a Mermaid ER diagram, gated in the existing consistency CI.
12. **Backup, restore, and PITR runbook for the Plan C schema.** `infra/` has no Postgres backup CronJob today (covered by `_infra.md` epic 13); on the database side we still need a documented `pg_dump`/`pg_restore` matrix per table (which to exclude, what hypertable chunks to dump), a PITR objective (RPO/RTO), a quarterly restore-drill checklist, and a `make restore-drill` target that exercises it against the dev stack. (Cross-edge: `_infra.md`.)
13. **Schema-evolution safety net: idempotency-aware backfills and online index builds.** No tooling today for `CREATE INDEX CONCURRENTLY`, batched backfills, or progress tracking; the spec assumes "every history/metric write uses `ON CONFLICT` upserts" (§6.7) but offers no template for adding a new metric column without locking writers. Add a backfill-job pattern in `backend/database/migrations/` and a `scripts/online_backfill.py` helper.

## Open questions

1. **Plan B storage shape.** Spec §3 (non-goals) carves out the API's `_workflow_projection` from this design; epic 1 implies a fresh Postgres schema for `workflow_runs`. Confirm whether the Postgres adapter mirrors the Redis hash layout (one row per run + per-update history) or denormalizes into a transition table — `RedisWorkflowRunStore` already encodes the contract.
2. **Tenant scoping shape.** Epic 8 assumes `tenant_id text NOT NULL` on every table with composite PK changes. Alternative: a `tenants` table + FK plus a single `current_tenant_id` GUC. Confirm whether RLS is in scope for v1 multi-tenancy or whether application-level filtering suffices initially (the answer drives whether composite-PK migrations have to land before any tenant work).
3. **Reader/writer DSN split vs single DSN with replica routing.** Epic 6 assumes a separate `READ_REPLICA_URL`. Alternative: a single DSN with `target_session_attrs=read-only` + pgpool. The choice affects `DatabaseConfig` shape and the composition-root wiring.
4. **TimescaleDB licensing.** Continuous aggregates and compression are Apache-licensed; some advanced retention features are TSL-only. Epic 9 needs confirmation that the deployment uses the OSS distribution (the dev compose image bundles both, which is fine in dev but may not survive a cloud-vendor managed-Postgres choice).
5. **Migration runner location.** `make migrate` runs `alembic upgrade head` from inside the API container (`Makefile:33`). In production should that live in (a) an init-container, (b) a dedicated Job/Helm hook, or (c) the API/worker boot path with an advisory lock? Epic 3 and `_cicd.md` both touch this; the choice changes how zero-downtime expand/contract pairs are sequenced.
6. **Schema ownership across modules.** `database/migrations/` owns the whole schema today, but `monitoring/`, `records/`, `analytics/*`, and (soon) `agent/`, `knowledgebases/` each effectively own a subset. Confirm whether to keep a single linear revision history or move to Alembic branch labels per module (cleaner ownership, harder cross-table changes).
