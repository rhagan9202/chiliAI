## File: docs/backlog/config.md

**Scope:** The `backend/config/` module — schema (`backend/config/schema.py`), loader (`backend/config/loader.py`), default bundles (`backend/config/defaults/*.yaml`), the `GET /config/*` API surface (`backend/api/routers/config.py`), and the frontend Configuration page (`chili_app/src/pages/ConfigurationPage.tsx`, `chili_app/src/api/config.ts`). Today the module is **read-only**: a single YAML/JSON file is resolved from `CHILI_CONFIG_PATH` (`backend/config/loader.py:51`), validated by Pydantic + an `after`-mode cross-reference validator (`backend/config/schema.py:400-540`), cached process-wide via `@lru_cache` (`backend/api/dependencies.py:312-321`), and served to the SPA as a JSON dump plus a derived `/features` payload and the live JSON schema (`backend/api/routers/config.py:24-45`). There is no write path, no overlay/merge, no hot reload, no migration, no per-tenant scoping, no plugin escape hatch, and the frontend Configuration page is a static read-only card view (`chili_app/src/pages/ConfigurationPage.tsx:8-94`).

### Epics
1. Reconcile `DomainConfig` schema with all module consumers — `DomainConfig` (`backend/config/schema.py:363`) exposes 17 sub-models but only `monitoring`, `analytics`, `records`, `auth`, `events`, `storage`, `graph`, `vectorstore`, `llm`, `embeddings`, `database`, `ui`, and `validation` are wired through DI in `backend/api/dependencies.py`; `IngestionConfig.chunking` (`backend/config/schema.py:90`) is parsed but never read by `IngestionService` (`backend/ingestion/service.py`) — `chunk_size`/`chunk_overlap` defaults live in code; `RagConfig.top_k`/`expansion_depth`/`reranking_enabled` (`backend/config/schema.py:205`) are not threaded into `RagService` either; `AlertsConfig.thresholds` (`backend/config/schema.py:217`) is declared as `dict[str, dict[str, float]]` but `MonitoringService` uses `MonitoringConfig.medium_threshold`/`high_threshold` and ignores the per-entity dict.
2. Resolve the `*_env_var` placeholder pattern centrally in the loader — `backend/config/loader.py:30` carries a `TODO(production)` for `${ENV_VAR}` placeholder resolution; today every adapter reads `os.environ[name]` itself (`backend/llm/factory.py`, `backend/graph/auth.py`, `backend/embeddings/adapters/openai_adapter.py`, `backend/storage/adapters/s3_adapter.py`) with no unified missing-env error, no startup-time validation that declared `*_env_var` names actually resolve, and no audit log of which secret names were consumed.
3. Deepen validation depth and cross-field constraints — current `_validate_cross_references` (`backend/config/schema.py:400`) covers duplicates, relationship endpoints, enum requirements, records-feed integrity, and the single vectorstore↔embeddings dimensions check; missing cross-field constraints include: `LlmConfig.provider="ollama"` requiring `base_url` (`backend/config/schema.py:122`), `OllamaLlmClient` will fail at runtime; `GraphDbConfig.backend="neo4j"` requiring `uri` and `auth_env_var` (`backend/config/schema.py:97-103`); `ObjectStoreConfig.backend in {"s3","minio"}` requiring `bucket` + `credentials_env_var` (`backend/config/schema.py:140`); `DatabaseConfig.backend="postgres"` requiring the env named by `dsn_env_var` to be set; `UiNavigationPageConfig.capability` (`backend/config/schema.py:229`) referencing only declared `CapabilitiesConfig` fields; `UiDisplayFieldsConfig.title`/`subtitle`/`chips` (`backend/config/schema.py:238`) referencing actual entity property names; `default_reference_kb_id` (`backend/config/schema.py:391`) referencing an existing KB at startup once the KB repository is available.
4. Support multi-environment config layering (base + dev/staging/prod overlay) — `backend/config/loader.py:30` carries a `TODO(production)` for "base + env-specific layer" merging; today `medicare_fraud.yaml` and `medicare_fraud_dev.yaml` (`backend/config/defaults/`) duplicate the entire entity/relationship/records surface to flip a handful of dev knobs; need a documented overlay strategy (deep-merge with list-replace semantics, `CHILI_CONFIG_OVERLAY_PATH` env, precedence rules), plus a way to express environment-specific backend selection without forking the file.
5. Add config hot-reload with cache invalidation across all consumers — `backend/config/loader.py:30` carries a `TODO(production)` for hot reload; `get_domain_config` is `@lru_cache(maxsize=1)` (`backend/api/dependencies.py:312`) and only cleared on `create_app()` (`backend/api/app.py:111`), so an admin who edits the YAML needs a process restart; downstream services (graph, vectorstore, llm, embeddings, monitoring, analytics, records) are also cached via `@lru_cache` and hold a config snapshot at construction. Need a `POST /config/reload` admin endpoint (called out in `backend/api/routers/config.py:18-21` `TODO(production)`), a file-watcher option, and a documented invalidation chain so caches downstream of `get_domain_config` are rebuilt atomically.
6. Move config persistence from filesystem YAML to a versioned write-through store — today config lives only as a YAML file on disk loaded via `Path.read_text` (`backend/config/loader.py:60-66`); endgame needs a DB-backed `domain_config` table (with `version`, `created_at`, `created_by`, `change_note`, and `payload` JSONB) accessed through a new `DomainConfigStore` protocol with both filesystem and Postgres adapters, plus a startup migration that bootstraps the table from the on-disk default. Required for the wizard (Epic 8), per-tenant config (Epic 11), and audit (Epic 9).
7. Add a config write API (POST/PUT `/config/domain`) with server-side validation — `backend/api/routers/config.py:18-21` carries the explicit `TODO(production)` for `POST /config/domain` (update) and `POST /config/reload` (reload). Today the router is GET-only with no admin write surface. Needs `require_role("admin")` (`backend/api/middleware/rbac.py:53`), full `DomainConfig.model_validate` of the submitted payload (re-raising the existing `ConfigLoadError`), a dry-run flag (`?validate_only=true`) so the wizard can pre-flight a draft, ETag / `If-Match` headers (also called out in `backend/api/routers/config.py:21`), and emission of a `config.updated` event for downstream cache invalidation (Epic 5).
8. Build the Configuration UI wizard end-to-end — `chili_app/src/pages/ConfigurationPage.tsx:8-94` is currently a static read-only card view showing entity count, capability flags, navigation page count, and schema section count; there is no entity/relationship editor, no capability toggle, no alert-threshold editor, no records-feed builder, no diff/preview, no save flow, no JSON-schema-driven form (`useDomainConfigSchema` is consumed only to count sections at `ConfigurationPage.tsx:87`). Wizard needs: schema-driven forms generated from `model_json_schema()`, an entity/relationship visual editor, validation-error display from the backend `ValidationError`, draft/save/publish lifecycle, and round-trip with the write API from Epic 7. Architecture §14.2 lists this at Medium priority.
9. Add config change audit log and history — there is no audit story today; `backend/api/routers/config.py:21` carries a `TODO(production)` for "change audit logging"; once Epic 6 adds the DB-backed store and Epic 7 adds the write API, every change must record `(actor user_id, tenant_id, version, change_note, diff, applied_at)`, and the wizard must expose history + rollback. Cross-edge to `_security.md` Epic 6 (durable audit log) and `database.md` (audit table migration).
10. Add config schema versioning and forward migration — `DomainConfig.schema_version: str = "1.0"` (`backend/config/schema.py:370`) is present but never read by the loader and never asserted; nothing migrates a stored config when a sub-model gains/renames/removes fields. Need a `config_migrations/` package with versioned `v1_0_to_v1_1.py` style transformers, a `migrate_to_current(payload, declared_version)` entry point invoked by `load_config` before `model_validate`, and a refusal-with-clear-error path for unknown future versions. Required so persisted configs from Epic 6 survive code upgrades.
11. Add tenant-scoped configuration loading and per-tenant overrides — `backend/config/loader.py:20` loads a single global config from `CHILI_CONFIG_PATH`; there is no tenant axis on the loader, the DI cache, the API routes, or the wizard. Endgame requires per-tenant resolution (likely keyed on the tenant claim from `_security.md` Epic 3), an overlay model (tenant overrides on top of platform defaults, scope-locked to a safe subset of fields), and per-tenant cache eviction. Hard cross-edge to `_multitenancy.md` Epic 2 (tenant binding on `DomainConfig`) and Epic 13 (per-tenant loading).
12. Add a plugin-config escape hatch in `DomainConfig` — `CapabilitiesConfig` (`backend/config/schema.py:49`) is a closed scalar-bool model and `AnalyticsConfig` (`backend/config/schema.py:189`) has no extension point, so a third-party plugin has nowhere to declare or persist its own configuration. Add a `plugins: dict[str, PluginConfig]` field with `enabled: bool`, `version_constraint: str`, and a typed `settings: BaseModel` validated against each plugin's declared `config_schema` after plugin discovery (so unknown plugin keys yield a clear error). Hard cross-edge to `_plugins.md` Epic 11.
13. Build export / import for domain packs (config + sample data bundle) — there is no export/import path today; an analyst who wants to share a custom domain has to copy the YAML by hand and reconstruct sample data separately. Need a "domain pack" bundle format (config YAML + manifest + optional sample documents + sample records feeds, e.g. a `.chiliai-pack` zip), `GET /config/export` (download pack), `POST /config/import` (validate + atomically install pack with conflict-on-existing-domain handling), and a CLI wrapper for offline pack management. Companion to the wizard (Epic 8) and to the bundled `medicare_fraud_cms_desynpuf.yaml` + `tools/sample_data/build_tennessee_subset.py` precedent for sample-data shipping.

### Open questions
- Where does authoritative threshold config live — `AlertsConfig.thresholds[entity_type][metric]` (per-entity, current schema shape in `backend/config/schema.py:217`) or `MonitoringConfig.medium_threshold`/`high_threshold` (flat scalars, currently the only path read at runtime in `backend/api/dependencies.py:610`)? Affects Epic 1's reconciliation direction and the wizard surface in Epic 8.
- Overlay merge semantics: deep-merge with list-replace (predictable, conservative) or list-merge-by-key (powerful but ambiguous for records.feeds and entities)? Affects Epic 4.
- Hot reload posture: file watcher (operator-friendly, OS-portable) vs. admin-triggered `POST /config/reload` only (auditable, explicit) vs. both? Affects Epic 5.
- DB-backed config persistence (Epic 6): is the filesystem default still loaded at startup as a bootstrap, or does the DB become the single source of truth as soon as the table exists (file becomes a one-shot seed)? Affects the migration story and rollback options.
- Wizard scope for v1 (Epic 8): full schema coverage (entities, relationships, capabilities, alert thresholds, records feeds, adapter backends) or read-mostly with a narrow "alert thresholds + capabilities + display fields" editable subset? Affects sequencing relative to Epic 7's dry-run mode.
- Schema migration triggers (Epic 10): automatic at startup (risky in prod) or admin-confirmed via `POST /config/migrate` (safer but adds an operational step)? Affects Epic 10's surface.
- Plugin config validation timing (Epic 12): does `DomainConfig.model_validate` block on plugin discovery (slower startup, single failure mode) or accept unknown `plugins.*` keys and validate lazily once the registry loads (more complex error reporting)? Affects ordering vs. `_plugins.md` Epic 2.
- Domain-pack format (Epic 13): single `.chiliai-pack` zip (operator-friendly, atomic) vs. a directory layout convention (git-friendly, diff-able)? Affects CLI ergonomics and the wizard's "import" UX.
- Should `default_reference_kb_id` (`backend/config/schema.py:391`) validation happen at config-load time (requires KB repo at startup — cyclic) or be deferred to a startup readiness probe? Affects Epic 3's enforcement point.
