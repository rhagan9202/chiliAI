## File: docs/backlog/_observability.md

**Scope:** Structured logging, Prometheus metrics, OpenTelemetry tracing, audit logging, frontend RUM/error tracking, and operator-facing dashboards/health endpoints — the cross-cutting telemetry surface defined in `docs/architecture.md` §11 plus the §14.2 audit-log capability.

### Epics
1. Adopt shared structlog across all backend modules — Only `api/app.py:30` and `agent/coordinator.py:160` import `shared.logging`; modules like `agent/health.py:7`, `ingestion/`, `graph/`, `rag/`, `monitoring/` still use stdlib `logging.getLogger(...)`, so correlation IDs and JSON output are inconsistent.
2. Add HTTP correlation-ID middleware and response-header propagation — `security_checklist.md:144` claims story E10-S09 propagates `correlation_id` as a response header, but `grep` for `X-Correlation` / `X-Request-Id` in `backend/api/` returns nothing; the contextvar in `shared/logging.py:28` is never seeded from inbound requests.
3. Propagate correlation-ID and W3C Trace Context across Redis Streams events — `shared/tracing.py:103` accepts a `correlation_id` attribute but no inject/extract helpers exist on the event bus; arch §11.3 requires "trace ID embedded in event metadata" for end-to-end pipeline traces.
4. Implement the architecture-defined Prometheus metric set — Only 5 of 7 metrics named in arch §11.2 exist (`http_requests_total`, `http_request_duration_seconds` in `api/middleware/metrics.py:29`; `pipeline_stage_duration_seconds`, `pipeline_errors_total`, `active_alerts_total` in `monitoring/metrics.py:25`). Missing: `pipeline_events_processed_total` (by event type), `graph_query_duration_seconds`, `alerts_generated_total` (by entity type & severity), `knowledgebase_documents_total`.
5. Instrument graph, vectorstore, embeddings, and LLM adapters with latency histograms — None of the adapter modules expose Prometheus instrumentation today; arch §11.2 specifically lists `graph_query_duration_seconds` and the pipeline-stage histogram should also cover embedding and LLM calls per stage label.
6. Wire OpenTelemetry spans across RAG, graph-expand, and LLM call paths — `setup_tracing()` runs at API/worker startup and `start_pipeline_span` exists (`shared/tracing.py:103`), but only the coordinator emits spans; `rag/service.py`, `graph/service.py`, and `llm/` adapters never call `get_tracer` or wrap their async calls.
7. Stand up an observability extra in dev compose (Prometheus + Grafana + Jaeger/Tempo) — `docker-compose.dev.yaml` and `infra/k8s/` have no Prometheus, Grafana, Jaeger, Tempo, or OTLP collector services; arch §11.2/§11.3 say Prometheus scrapes `/metrics` and OTLP exports to Jaeger/Tempo.
8. Ship default Grafana dashboards and Prometheus alert rules — Nothing exists yet; without curated dashboards the new metrics (pipeline throughput, DLQ rate, alert generation, graph-query latency) cannot be consumed and the `security_checklist.md:151` claim that "alerting on the DLQ rate is the primary integrity signal" has no implementation.
9. Split `/health` from `/ready` and add deep readiness probes — `api/app.py:137` returns a hard-coded `{"status": "ok"}`; worker health (`agent/health.py:60`) only tracks "last event processed". K8s liveness and readiness both point at `/health` (`infra/k8s/chili-api-deployment.yaml:47,55`) so a degraded dependency (Neo4j/Redis/Qdrant) is invisible to the orchestrator.
10. Add a structured audit-log subsystem — `grep` for `audit_log` returns zero results; arch §14.2 ranks audit log as Medium priority for tracking analyst actions (graph queries, alert acks, config changes) for compliance, and `security_checklist.md` A09 references it as outstanding.
11. Integrate frontend error tracking and Web Vitals (Sentry/equivalent) — `chili_app/` has no Sentry/Datadog dependency and the only handler is the stub `ErrorBoundary` at `chili_app/src/components/common/ErrorBoundary.tsx:24` that just `console.error`s; arch §11.4 calls for Sentry and §13 lists it as the production-hardening front-end stack.
12. Make tracing/metrics tenant- and KB-aware — Existing metrics use only `method`/`path`/`stage` labels (`api/middleware/metrics.py:32`, `monitoring/metrics.py:28`); arch §12.3 multi-tenancy and §7 KB scoping require per-tenant / per-KB attribution so observability matches the access-control boundary.
13. Document and enforce a logging-and-metrics conventions guide — `docs/onboarding.md` has no log-level or metric-naming guidance; without a written contract the per-module rollout (epic 1) and metric additions (epic 4) drift, and the architecture's "INFO request lifecycle / WARNING degraded / ERROR failures" rule (§11.1) is not codified anywhere developers will read.

### Provisional cross-file edges
- Make tracing/metrics tenant- and KB-aware depends on tenant-scope plumbing in `_multitenancy.md` — labels need a tenant ID source.
- Add a structured audit-log subsystem depends on RBAC user-identity capture in `_security.md` — audit entries must record the authenticated principal.
- Stand up an observability extra in dev compose depends on infra manifests in `_infra.md` — K8s/Helm charts must add Prometheus/Grafana/Jaeger resources for production parity.
- Split `/health` from `/ready` and add deep readiness probes depends on dependency-health checks that touch `database.md`, `graph.md`, `vectorstore.md`, `events.md` adapters — readiness must probe each backing store.
- Implement the architecture-defined Prometheus metric set has fan-out into `monitoring.md` (alerts_generated_total labels), `knowledgebases.md` (knowledgebase_documents_total gauge), `events.md` (pipeline_events_processed_total counter), and `graph.md` (graph_query_duration_seconds histogram) — each owning module supplies the instrumentation point.
- Integrate frontend error tracking and Web Vitals depends on `frontend.md` build/runtime config — SDK init, source maps, and release tagging live in the SPA build pipeline.
- Ship default Grafana dashboards and Prometheus alert rules depends on `_cicd.md` — dashboards/alert rules ship as code reviewed and deployed through CI.

### Open questions
- Sentry vs. self-hosted GlitchTip vs. OpenTelemetry-only for the frontend — arch §11.4 and §13 say "Sentry or equivalent" but don't lock the vendor; this affects whether RUM stays in the observability epic or splits.
- Where audit-log events are persisted (Postgres table vs. dedicated event stream vs. external SIEM) — arch §14.2 lists the capability but not the storage substrate; downstream stories in `database.md` / `events.md` depend on this.
- Whether `correlation_id` and W3C `trace_id` should be unified or remain parallel identifiers — `shared/tracing.py:125` currently sets `correlation_id` as a span attribute rather than mapping it onto `trace_id`; clarifying this changes the propagation epic's contract.
- Whether the `/metrics` endpoint should remain `require_role("service")`-gated (`api/middleware/metrics.py:99`) or move to a separate internal-only port, which affects how Prometheus is configured in the dev/prod compose epic.
