## File: docs/backlog/analytics.md

**Scope:** All five analytics subpackages — `analytics/timeseries`, `analytics/gnn`, `analytics/risk`, `analytics/explainability`, `analytics/metrics` — plus the analytics API surface (`backend/api/routers/analytics.py`) and worker write-back/throttle integration in `backend/agent/coordinator.py`. Covers algorithm production-readiness, persistence wiring, model-training pipeline (§14.2), feedback loop into the graph (§6.7), and observability integration. Does not own evidence-pack persistence outside the evidence-pack model (lives in `api`/persistence layers) or alert generation (lives in `monitoring`).

### Epics

1. GNN: Replace degree-centrality scoring with real GNN inference — `_score_nodes()` is normalized degree-plus-feature-magnitude and `_predict_links()` is cosine similarity, with a `TODO(production)` flagging the gap (`backend/analytics/gnn/service.py:46-50,187-237`).
2. GNN: Persist trained model artifacts and serve from durable storage — `GnnService` re-runs Louvain + spectral embedding on every `analyze()` call with no model cache, snapshot reuse, or artifact location (`backend/analytics/gnn/service.py:63-146`, `backend/analytics/gnn/adapters/in_memory.py:11-44`).
3. GNN: Add Neo4j/graph-backed `GraphSnapshotSourceProtocol` adapter — only `InMemoryGraphSnapshotSource` exists; the protocol `TODO(production)` calls for graph-derived snapshots and incremental loading, and `get_graph_snapshot_source()` always returns the in-memory source (`backend/analytics/gnn/adapters/protocols.py:14-21`, `backend/analytics/gnn/adapters/in_memory.py`, `backend/api/dependencies.py:660-662`).
4. GNN: Stream and bound large-graph analysis — `_compute_embeddings` builds a full `node_count × node_count` Laplacian and calls `np.linalg.eigh` (O(n³) memory and time), and `_predict_links` is O(n²); both will OOM on production-sized KBs (`backend/analytics/gnn/service.py:287-345,214-237`).
5. GNN: Surface in-graph `ClusterSummary` persistence (no real cluster source) — `list_clusters` reads `load_clusters`, but `InMemoryGraphSnapshotSource.load_clusters` returns whatever was put in via test fixtures and no production adapter writes cluster summaries to the graph or a store (`backend/analytics/gnn/service.py:149-169`, `backend/analytics/gnn/adapters/in_memory.py:31-44`).
6. Timeseries: Add Postgres `load_series` for per-entity (not graph-scope) metrics — `PostgresTimeSeriesHistorySource._SERIES_SQL` selects from `entity_metric_history`, but Flow 2 only writes graph-scope metrics keyed on `entity_id="__graph__"`, so per-entity metric series have no producer (`backend/analytics/timeseries/adapters/postgres.py:17-30`, `backend/analytics/metrics/models.py:11-16`, `backend/agent/coordinator.py:1096-1300`).
7. Timeseries: Wire production `PostgresTimeSeriesHistorySource` through API DI — `get_timeseries_history_source()` is hardcoded to `InMemoryTimeSeriesHistorySource()`; analytics router never reads the Postgres adapter that already exists (`backend/api/dependencies.py:644-647`, `backend/analytics/timeseries/adapters/postgres.py:33-94`).
8. Timeseries: Add forecasting/probabilistic models alongside detection — `DetectionStrategy` is limited to `z_score | stl_decomposition | isolation_forest` and surfaces no Prophet/ARIMA/probabilistic forecasting, but architecture §6.2 expects time-series analysis to feed risk scoring with predicted vs. observed deltas (`backend/analytics/timeseries/service_models.py:11`, `backend/analytics/timeseries/service.py:168-195`).
9. Risk: Replace linear weighted-sum strategy with ML-backed scorers — `LinearScoringStrategy.score` is a deterministic normalized linear combination; `RiskScoringStrategyProtocol` supports pluggable strategies but no XGBoost/learned model adapter exists (`backend/analytics/risk/adapters/linear_strategy.py:8-22`, `backend/analytics/risk/protocols.py:25-29`).
10. Risk: Add graph-derived and vectorstore-derived `RiskSignalSource` adapters — protocol carries a `TODO(production)` calling for graph + vectorstore signal computation; only `InMemoryRiskSignalSource` exists and the API DI always returns it (`backend/analytics/risk/adapters/protocols.py:14-17`, `backend/analytics/risk/adapters/in_memory.py:10-67`, `backend/api/dependencies.py:626-629`).
11. Risk: Back `RiskSignalSource` reads with Postgres history — `PostgresRiskHistoryStore` is writer-only plus `load_historical_score`; full `RiskSignalSourceProtocol` Postgres backing is explicitly deferred per architecture §6.4 Plan C deviations and protocol docstring (`backend/analytics/risk/adapters/postgres.py:45-87`, `backend/analytics/risk/adapters/protocols.py:37-54`, `docs/architecture.md:715`).
12. Risk: Promote graph-native history nodes alongside the entity-property snapshot — Flow 3 writes flat `risk_score`/`risk_level`/`risk_assessed_at` properties to entities; graph-native history nodes linking entities to historical assessments are deferred per architecture §6.4 (`backend/agent/coordinator.py:1478-1530`, `docs/architecture.md:716`).
13. Explainability: Generate LLM narrative reasoning beyond join-of-rationales — `_build_reasoning` joins string rationales with spaces; `_build_narrative` groups by `source_type` only, no LLM narration despite `TODO(production)` (`backend/analytics/explainability/service.py:30-33,115-148`).

Explainability: Wire SHAP adapter and add LIME/saliency alternatives behind `ExplainabilityContextSourceProtocol` — `ShapExplainabilityContextSource` exists but is never registered in API DI; only `InMemoryExplainabilityContextSource` is constructible from the API surface, and no LIME/permutation-importance adapter exists (`backend/analytics/explainability/adapters/shap_adapter.py:97-158`, `backend/api/dependencies.py` (no `get_explainability_*`)).

Explainability: Expose `/explainability/{alert_id}` API + DI — analytics router has zero explainability endpoints; `ExplainabilityService` is only invoked via the SSE/state path indirectly, with no `get_explainability_service` in `api/dependencies.py` (`backend/api/routers/analytics.py:1-133`, `backend/api/dependencies.py:617-682`).

17. 18. Metrics: Expand graph-scope metrics beyond entity/relationship/avg-degree — `models.py` defines only `METRIC_ENTITY_COUNT`/`METRIC_RELATIONSHIP_COUNT`/`METRIC_AVG_DEGREE`; betweenness, PageRank, community quality, and per-entity-type breakdowns are not collected (`backend/analytics/metrics/models.py:11-16`, `backend/agent/coordinator.py:1096-1300`).
19. Metrics: Add a Prometheus/OpenMetrics exposition surface — `analytics/metrics/` is persistence only (history + current tables); no `/metrics` endpoint, no `prometheus_client` integration, no scraper-readable counters for analytics throughput/latency despite §14.2 observability ambition (`backend/analytics/metrics/__init__.py`, `backend/analytics/metrics/adapters/protocols.py:11-27`).

21. ### Provisional cross-file edges

- "Wire production `PostgresTimeSeriesHistorySource` through API DI" and "Back `RiskSignalSource` reads with Postgres history" depend on `database.md` migrations for `entity_metric_history` and `risk_score_history` (already shipped, but the adapters need DI selection logic that the database epics formalize).
- "Add Postgres `load_series` for per-entity metrics" depends on `monitoring.md` and `records.md` `observations` write-path — per-entity metrics currently come from `observations` (not `entity_metric_history`), so the read adapter needs a shared source-of-truth contract.
- "Add Neo4j/graph-backed `GraphSnapshotSource` adapter" depends on `graph.md` neighborhood/whole-KB export surface — `GraphServiceProtocol` does not yet expose a full-KB snapshot read suitable for GNN.
- "GNN: Stream and bound large-graph analysis" depends on `graph.md` paginated/iterator reads and `_observability.md` saturation metrics (to know when to back off).
- "Generate LLM narrative reasoning" and "Add a graph + RAG + risk subgraph assembler" depend on `llm.md` (narration), `rag.md` (top-k retrieval), and `graph.md` (subgraph extraction) cross-module read protocols.
- "Wire SHAP adapter and add LIME/saliency alternatives" depends on `config.md` adapter selection epics to let `DomainConfig.analytics.explainability_backend` pick the implementation.
- "Persist generated evidence packs durably" depends on `database.md` for a new `evidence_pack_history` migration and `api.md` for `/evidence/{pack_id}` read endpoints (today `evidence.py` router exists but has no persistence layer).
- "Add per-stage analytics metrics, traces, structured logs" depends on the cross-cutting telemetry stack in `_observability.md`.
- "Add a Prometheus/OpenMetrics exposition surface" depends on `_observability.md` (decision on `/metrics` endpoint location, scrape config, label conventions).
- "Write GNN cluster / link predictions back to graph" and "Write timeseries anomaly flags back to graph" depend on `agent.md` epic for new coordinator handlers, `events.md` for any new analytics-derived event fields, and `graph.md` for new entity property contracts (`cluster_id`, `predicted_neighbor_ids`, `last_anomaly_at`).
- "Model training pipeline" epics (21–23) depend on `agent.md` for scheduled/triggered job runners, `storage.md` for model artifact persistence (S3/MinIO), `database.md` for a model-registry migration, and `config.md` for typed `DomainConfig.analytics.training` block.
- "Add Postgres-backed `RiskSignalSource` reads" depends on `monitoring.md` `PostgresObservationSource` contract (signals will likely derive from monitoring observations).
- "Add `POST /analytics/...` write endpoints" depends on `api.md` route policy registry + `_security.md` RBAC scope expansion (writes are likely investigator/admin, not viewer).
- "Remove deterministic-payload shortcut endpoints" depends on `frontend.md` migrating Dashboard/EntityDetail to live projections (architecture §8.1 calls out seeded read models that need migrating).
- "Production guardrails: reject in-memory adapters in production" depends on `_security.md` / `config.md` production-mode guardrail epic.

### Open questions

- Should the model training pipeline (§14.2) live in `analytics/training/` as a sixth subpackage, or in `agent/` as a new pipeline kind, or in a separate top-level `training/` module? Architecture §5.2 says "no business logic in `agent/`", suggesting `analytics/training/`, but training crosses GNN + embeddings + risk-strategy scopes.
- Where do trained model artifacts live: `storage/` (object store), Postgres (`model_registry` table), or both (registry metadata in PG, blobs in object store)? Architecture §14.2 doesn't pick one; Plan C precedent (history in PG, snapshots on graph) suggests PG metadata + object-store blobs.
- Should evidence packs be persisted by the explainability service (write-through) or by a worker handler `handle_explainability_generated_for_storage` (mirrors Plan C Flow 3/4)? The Plan C pattern strongly suggests the handler approach.
- Per-entity timeseries: should `analytics/timeseries` read from `observations` (monitoring's table) or `entity_metric_history` (analytics/metrics' table)? Today `PostgresTimeSeriesHistorySource` queries `entity_metric_history` but Flow 2 only writes graph-scope rows there; per-entity history has no producer.
- Should the GNN snapshot adapter write back GNN-derived embeddings to the vectorstore (so RAG queries inherit graph-structural similarity), or remain read-only? Architecture §6.7 implies feedback but doesn't specify the vectorstore path.
- Should `analytics/metrics` be renamed (e.g. `analytics/metric_store` or `analytics/persistence`) to avoid name collision with the operational/Prometheus "metrics" concept that epic 19 introduces? The README already flags the package as "intentionally smaller" and not algorithmic.
- Does Louvain (`networkx.community.louvain_communities`) need to be replaced before the GNN epic land (it's CPU-bound and single-threaded), or is it acceptable as the heuristic baseline until the real GNN training pipeline is wired?
