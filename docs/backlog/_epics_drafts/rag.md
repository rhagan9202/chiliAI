## File: docs/backlog/rag.md

**Scope:** Retrieval-augmented answer generation for `backend/rag/` — pipeline orchestration in `service.py`, the four pluggable ports in `adapters/protocols.py` (`QueryEmbedderProtocol`, `ContextRetrieverProtocol`, `GraphContextExpanderProtocol`, `AnswerGeneratorProtocol`), the deterministic `adapters/in_memory.py` fakes (`InMemoryQueryEmbedder`, `InMemoryContextRetriever`, `InMemoryGraphContextExpander`, `InMemoryAnswerGenerator`, `InMemoryRagService`), workflow/transport models (`models.py`), service-boundary DTOs (`service_models.py`), the exception ladder (`exceptions.py`), and the `RagCompletedEvent` published on every answer (`backend/events/types.py:229-241`). Composition lives in `backend/api/_rag_bridges.py` (the four `Service*` bridges that connect RAG ports to embeddings/vectorstore/graph/llm services per architecture §5.2 — RAG cannot import sibling feature modules directly) and `backend/api/state.py:172-178` (the only place a `RagService` is actually constructed today). Excludes the chat conversation read model itself and the `/chat/conversations[/...]` routes (owned by `api.md`), the vector store and LLM adapter internals (`vectorstore.md` / `llm.md`), and embedder adapter selection (`embeddings.md`).

### Epics
1. Wire the live `RagService` (service-backed `Service*` bridges) into the API and retire the seeded `InMemoryRagService` fallback path — `ApiState.__init__` at `backend/api/state.py:172-178` builds the production `RagService` from `InMemoryQueryEmbedder` + `InMemoryContextRetriever(records=self._build_context_records())` + `InMemoryAnswerGenerator(provider="in-memory", model_name="seeded-rag-model")` + `InMemoryGraphContextExpander()`, even though `backend/api/_rag_bridges.py` already ships `ServiceQueryEmbedder` (`:55-101`), `ServiceContextRetriever` (`:104-142`), `ServiceGraphContextExpander` (`:145-211`), and `ServiceAnswerGenerator` (`:214-279`) — none of them are referenced by `backend/api/dependencies.py` (no `get_rag_service` factory exists), so the only seeded context records are two Medicare provider strings (`backend/api/state.py:830-846`) and every analyst RAG turn echoes `"Answer based on N context items: <question>"` (`InMemoryAnswerGenerator._compose_answer` at `backend/rag/adapters/in_memory.py:220-225`). Add a `get_rag_service()` DI factory composing the four bridges with the configured embeddings, vectorstore, graph, and llm services, route `ApiState.add_message`/`stream_answer` through it, and delete `InMemoryRagService` from the production code path (keep it only for tests). Cross-edge to `vectorstore.md`, `llm.md`, `embeddings.md`, `graph.md`, `api.md`.

2. Fan retrieval, embedding, and graph expansion out across the full KB scope instead of collapsing to `knowledge_base_ids[0]` — `RagService._prepare_state` deliberately picks `primary_kb_id = request.knowledge_base_ids[0]` and embeds + retrieves against only that KB (`backend/rag/service.py:130-149`), `_build_generation_request` passes the same scalar to the generator (`backend/rag/service.py:166-173`), `_expand_graph_context` does the same for graph expansion (`backend/rag/service.py:199-202`), and `_publish_completed_event` flattens the multi-KB request into a single `knowledge_base_id` on the event (`backend/rag/service.py:217-228`). The dual-graph contract (`docs/architecture.md:810`) explicitly says RAG must span the full `resolve_kb_scope` list (primary transactional KB + reference policy KB) and that cross-KB joining is the consumer's responsibility — today the reference KB is fetched at the router (`backend/api/routers/rag.py:97`) and then silently dropped at the first line of `_prepare_state`. `VectorSearchRequest` already accepts `knowledge_base_ids: list[...]` (used by `ServiceContextRetriever` at `backend/api/_rag_bridges.py:121-126`) so retrieval can fan out without a protocol break; the embedder and graph expander protocols need a multi-KB signature or per-KB fan-out loop.

3. Pull `top_k`, `expansion_depth`, and `reranking_enabled` from `RagConfig` instead of request defaults and inert literals — `RagConfig` (`backend/config/schema.py:205-211`) declares `top_k: int = 5`, `expansion_depth: int = 2`, and `reranking_enabled: bool = False`, but `RagQueryRequest.top_k` defaults to 5 in the request model itself (`backend/rag/service_models.py:27`) and `RagService` never reads `domain_config.rag.top_k`. `expansion_depth` is wired into nothing — `ServiceGraphContextExpander.__init__(depth=1)` is constructed with a literal default at `backend/api/_rag_bridges.py:152-157` and is the only consumer of the depth concept. `reranking_enabled` is referenced in the schema and the YAMLs (`backend/config/defaults/medicare_fraud.yaml:159-162`) but no code path inspects it — see epic 9. Adopt `RagConfig` as the source of truth, override only when the request explicitly sets a value.

4. Add an `AnswerCitationProtocol` so citations name the actual source passages the LLM used, not the full retrieval set — `_build_citations` (`backend/rag/service.py:253-256`) just sorts every retrieved item by descending score and returns all of them as `RagCitation`s, even items the answer never referenced and items truncated out by `_fit_context_to_budget` in `ServiceAnswerGenerator` (`backend/api/_rag_bridges.py:334-375`). The frontend chat bubble (`chili_app/src/pages/RagChatPage.tsx:146-152`) renders every `citation_id`, so analysts see "supporting" chips for retrieval matches that were never in the prompt. Add a structured citation extraction pass (LLM-emitted `[n]` markers in the prompt at `backend/api/_rag_bridges.py:312-331` parsed back out, or a second LLM call that maps the answer to the retrieved set), surface `cited_record_ids` distinct from `retrieved_record_ids`, and update the chat citation chips to render only cited items.

5. Carry conversation history into the prompt so multi-turn investigations work — `RagService.answer` accepts `RagQueryRequest` (`backend/rag/service.py:66`), which has no `conversation_id`, no history, and no message turns; `ServiceAnswerGenerator.generate` builds the chat from exactly two messages (`SYSTEM` + a single `USER` containing only the current question and context: `backend/api/_rag_bridges.py:262-267`). `ApiState.add_message` appends the user message to `ConversationRecord.messages` then calls `_rag_service.answer(...)` with only `request.content` (`backend/api/state.py:434-466`), so each turn is independent and the assistant cannot refer back to previous answers, narrow a previous result set, or maintain investigation context. Extend `RagQueryRequest` (or add a `RagFollowUpRequest`) to carry prior turns, append them as `ChatMessageInput` in the LLM call, and decide on a history-window/truncation policy that interacts with epic 12 (token budget).

6. Replace the synchronous `stream_generate → yield result.answer` stub with token-level streaming — `ServiceAnswerGenerator.stream_generate` calls `self.generate(request)` and yields the full answer as one chunk (`backend/api/_rag_bridges.py:277-279`), and the route `_stream_sse` (`backend/api/routers/rag.py:108-122`) consumes that single chunk and emits it as one SSE event followed by the final `done` sentinel — analysts get the spinner, then a wall of text. `LlmServiceProtocol` already needs a `stream_generate` for this to be real (cross-edge to `llm.md`); plumb iterator chunks from the LLM client through `AnswerGeneratorProtocol.stream_generate` and the SSE encoder, and update `RagStreamChunk` semantics so non-final chunks are tokens, final chunks carry citations + usage. Cross-edge to `api.md` (SSE epic 7, event-driven push semantics).

7. Implement a reranking stage (cross-encoder or LLM-judge) gated by `RagConfig.reranking_enabled` — `ContextRetrieverProtocol` carries a `TODO(production)` calling out hybrid search + reranking as missing (`backend/rag/adapters/protocols.py:22-25`), and `RagService` has no rerank step between retrieval and prompt assembly. Add a `RerankerProtocol` (input: query + retrieved items, output: re-scored items with optional rationale), an `InMemoryReranker` for tests, an LLM-based default adapter, and a cross-encoder adapter (sentence-transformers `CrossEncoder`); insert it between `_prepare_state` and `_build_generation_request` and respect the config flag. Cross-edge to `llm.md` (judge LLM) and `embeddings.md` (sentence-transformers reuse).

8. Add hybrid retrieval (vector + keyword + graph signals) behind a unified `ContextRetrieverProtocol` — current retrieval is pure dense-vector cosine match through `ServiceContextRetriever` (`backend/api/_rag_bridges.py:104-142`) and `InMemoryContextRetriever._cosine_similarity` (`backend/rag/adapters/in_memory.py:238-247`); there is no BM25/keyword path, no fulltext fallback, and graph proximity (e.g., entity overlap with a named entity in the question) is only attempted post-retrieval in `ServiceGraphContextExpander._extract_entity_id` (`backend/api/_rag_bridges.py:282-287`). Add a `HybridRetriever` composite that fans out to vector + keyword (Neo4j fulltext as in `graph.md`, or a Qdrant payload-keyword filter) + graph-entity match, fuses with RRF or weighted score, and respects `RagConfig`. Cross-edge to `vectorstore.md` (keyword-payload search), `graph.md` (fulltext entity search), `embeddings.md`.

9. Honor per-KB RAG scoping in the worker and tests so RAG queries are bounded by KB access — `resolve_kb_scope` (`backend/shared/kb_scope.py:30-66`) is called once at the chat router (`backend/api/routers/rag.py:97`), and `ApiState.add_message` also calls it (`backend/api/state.py:450`), but no other RAG entry point does — `RagService.answer_question` (`backend/rag/service.py:91-107`) takes raw `knowledge_base_ids` from the caller and never validates KB existence, ownership, or tenant binding; `InMemoryRagService._require_known_kb` is the only existence check and it's optional (`backend/rag/adapters/in_memory.py:200-207`). Add KB-existence + access-policy enforcement inside `RagService` (or a thin guard in front of it), reject unknown / unauthorized KBs with `RagConfigurationError`, and ensure every RAG entry point routes through `resolve_kb_scope`. Cross-edge to `knowledgebases.md` (KB existence check), `api.md` (RBAC), `_security.md`.

10. Add a RAG quality evaluation harness with gold Q/A regression — there is no `backend/rag/evals/` package, no Ragas/Trulens scaffolding, no gold-question fixtures under `backend/tests/` beyond unit-level retrieval matchers, and `backend/rag/notes` is empty. Cite `docs/architecture.md:1346` ("RAG quality depends heavily on embedding model choice") — without a regression harness, embedding swaps, prompt tweaks, and reranker introduction cannot be evaluated. Add a `tools/rag_eval.py` (or `backend/rag/evals/`) that loads a gold set per domain, runs retrieval + generation, computes recall@k, MRR, citation precision, and answer-similarity, persists results under `docs/rag-evals/`, and fails CI on regression beyond a configurable delta. Cross-edge to `_cicd.md`.

11. Track LLM + embedding cost per RAG query and roll up per user/per KB/per tenant — `ServiceAnswerGenerator.generate` returns only `RagGenerationResult{request_id, answer, provider, model_name}` (`backend/api/_rag_bridges.py:240-275`) and `RagQueryResponse` (`backend/rag/service_models.py:51-60`) carries no token usage, no cost, no input/output token counts. The `RagCompletedEvent.replies` payload (`backend/events/types.py:229-241`) records `context_item_count`, `citation_count`, `answer_length` but nothing billable. Add `TokenUsage{prompt, completion, total, estimated_cost_usd}` on `RagGenerationResult`, propagate to `RagQueryResponse` and the event reference, persist per-query usage, and expose roll-ups. Cross-edges to `llm.md` (provider must report token counts), `embeddings.md` epic 5, `_observability.md`, `_multitenancy.md` (per-tenant attribution).

12. Make token-budget assembly first-class instead of a constant-divided heuristic — `ServiceAnswerGenerator._fit_context_to_budget` (`backend/api/_rag_bridges.py:334-375`) computes `budget_chars = int(self._max_tokens * 0.8) * 4` using module constants `_CHAR_PER_TOKEN = 4` and `_BUDGET_FRACTION = 0.8` (`backend/api/_rag_bridges.py:38-40`), then drops items greedily by score and rough-truncates the last one at `_MIN_TRUNCATED_CONTENT_CHARS = 16` (`backend/api/_rag_bridges.py:40,366`). There is no real tokenizer call (no `tiktoken`/SentencePiece), no per-model context-window awareness (`max_tokens` is the generation cap, not the model window), no separate accounting for `graph_context.summary`, no fallback when the question alone exceeds the window, and no map-reduce / hierarchical summarization for long contexts. Replace the heuristic with a real per-provider tokenizer, add model-context-window registry (cross-edge to `llm.md`), implement a summarize-then-stuff fallback for over-budget inputs, and surface "context dropped" + "items truncated" as observability signals.

13. The `TODO(production)` at `backend/rag/service.py:43-47` enumerates the missing surface (retries, timeouts, circuit breakers, memoization) and none of it exists. Add an OTel span per pipeline stage (`embed_query`, `retrieve`, `rerank`, `expand_graph`, `assemble_prompt`, `generate`, `stream`), Prometheus counters/histograms for each, structured logs with `request_id` + `knowledge_base_ids` + token usage, and a `/metrics` surface so dashboards can graph p50/p95 per stage. Cross-edge to `_observability.md`, `events.md` (W3C trace propagation onto `RagCompletedEvent`).

14. 15. Cross-edge to `api.md` epic 18 (gateway rate-limit middleware), `_security.md`, `_multitenancy.md`.

16. Cache the assembled system prompt + per-KB context block and reuse LLM provider prompt caching where available — `_DEFAULT_SYSTEM_PROMPT` is recomputed at `backend/api/_rag_bridges.py:34-37` per request and `_resolve_system_prompt` re-renders the domain-config template via `_render_system_prompt` (`backend/rag/service.py:175-187, 308-318`) on every call with no memoization. `_assemble_prompt` (`backend/api/_rag_bridges.py:312-331`) rebuilds the full context block per request. ### Open questions
- Should the live wiring (epic 1) flip `ApiState`'s singleton over wholesale, or should we keep a `CHILI_RAG_PROFILE=seeded|live` toggle so demos and tests still get the deterministic canned answers? The seeded `_build_context_records` (`backend/api/state.py:830-846`) is also the only data that makes the chat page non-empty without an end-to-end ingestion+embed pipeline.
- For multi-KB fan-out (epic 2), do we (a) call retrieval once with the full `knowledge_base_ids` list (current `VectorSearchRequest` shape), (b) call once per KB and fuse with RRF / weighted-merge, or (c) treat the reference (policy) KB as a second-pass enrichment after the primary retrieves? Each has different implications for `top_k` semantics, score comparability across KBs, and per-KB attribution on citations.
- For citation extraction (epic 4), do we ask the LLM to emit numeric markers (`[1]`, `[2]`) that we parse out (cheap, brittle), use JSON-mode / structured-output to return `{answer, citations[]}` (cleaner, more provider-specific), or run a second judge LLM pass that maps the answer to the retrieved set (most accurate, doubles cost)?
- For conversation history (epic 5), do we summarize older turns into a rolling memory once the window fills, drop oldest first, or carry the raw transcript and let epic 12's budget squeezer truncate? Each affects the believability of long investigations.
- For the reranker (epic 7), does `RagConfig.reranking_enabled` carry a `reranker_backend` field (literal: `none | cross_encoder | llm_judge`) so domains can pick, or do we ship a single default and add config later? The latter is simpler but locks in cost/latency choices.
- For hybrid retrieval (epic 8), do we expose `RagQueryRequest.retrieval_mode` to callers (analyst can toggle vector-only vs hybrid for a single question) or treat it as a domain-config-only knob? The former is great for debugging, terrible for prompt caching.
- For evals (epic 10), do gold question sets live in the repo under `backend/tests/fixtures/rag_gold/` (versioned, public) or in object storage referenced by domain config (private per deployment)? Medicare fraud gold sets may contain sensitive language.
- For prompt caching (epic 16), do we adopt the OpenAI / Anthropic native prompt-cache headers (provider-specific, no chiliAI code beyond the marker), build our own KV cache keyed by prompt hash (provider-agnostic, second cost), or both layered? The architecture endgame implies "both" but ordering matters for epic 1 sequencing.
- For tenant scoping (epic 17), does the RAG service become per-tenant (one `RagService` instance per tenant with bespoke wiring/quotas) or stay singleton with tenant as a request parameter? Per-tenant is cleaner for quota+cache isolation but multiplies process memory.
- The four `Service*` bridges live in `backend/api/_rag_bridges.py` to keep `rag/` free of sibling-module imports per architecture §5.3. Do they stay there forever, or do they move into `rag/adapters/` once we accept that the protocol+adapter rule was meant for external systems (DB, LLM) rather than sibling services, and the indirection costs us discoverability? Affects where new bridges (reranker, hybrid retriever, citation extractor) live.
