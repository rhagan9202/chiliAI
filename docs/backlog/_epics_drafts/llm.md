## File: docs/backlog/llm.md

**Scope:** LLM client abstraction and prompt management for `backend/llm/` and the composition seams that wire it into RAG answer generation (`backend/api/_rag_bridges.py`), LLM-driven entity extraction (`backend/ingestion/extractor.py`), and the worker coordinator (`backend/agent/coordinator.py`). Covers adapter parity (in-memory, OpenAI, Anthropic, Ollama; vLLM roadmap), fallback-chain robustness, prompt-template versioning, structured-output / JSON mode, native streaming, context-window management, function/tool calling, response caching, cost & token observability, rate-limit handling, multi-model routing, and prompt-injection defense. Excludes RAG retrieval/grounding (owned by `rag.md`) and embedding generation (owned by `embeddings.md`).

Done and intentionally **not** carried forward as epics:
- OpenAI / Anthropic rate-limit detection + exponential backoff up to 3 attempts (`backend/llm/adapters/openai_adapter.py:103-129`, `anthropic_adapter.py:103-131`).
- Recursive fallback-chain construction with graceful "skip provider that fails to construct" semantics (`backend/llm/factory.py:60-92`).
- `FallbackLlmClient` tries primary then each fallback on `LlmProviderError`, raising aggregate after exhaustion with structured warnings (`backend/llm/adapters/fallback.py:31-47`).
- Ollama JSON-decode + non-200 + empty-body error mapping to `LlmProviderError` (`backend/llm/adapters/ollama_adapter.py:40-63`).
- `LlmCompletedEvent` publish on every successful generation with KB id, request id, model, provider, message count, completion length (`backend/llm/service.py:53-66`, `backend/events/types.py:202-213`).
- Adapter-layer optional `prompt_tokens` / `completion_tokens` capture into `CompletionMetadata` for OpenAI and Anthropic (`backend/llm/models.py:45-49`, `openai_adapter.py:84-89`, `anthropic_adapter.py:84-89`).

### Epics
1. Add provider-native token streaming through the adapter and service surface — `LlmClientProtocol` only declares `generate`, the `TODO(production)` calls out missing `stream_generate`, and `LlmService.generate_stream` is a documented one-shot fallback that yields the full completion as a single chunk; `RagService.stream_answer` and the SSE chat endpoint advertise streaming but actually wait for the whole response (`backend/llm/adapters/protocols.py:14-21`, `backend/llm/service.py:69-79`, `backend/api/_rag_bridges.py:277-279`, `backend/api/routers/rag.py:99-122`).
2. Add structured-output / JSON-mode support across adapters and contract it through `GenerationRequest` — Ingestion extractor relies on prompt-engineered "Return JSON only" and post-hoc `_strip_json_fences` + `json.loads`, surfacing `LLM returned non-JSON for chunk` warnings instead of using OpenAI `response_format={"type": "json_object"}`, Anthropic JSON schemas, or Ollama `format: "json"` (`backend/ingestion/extractor.py:288-302`, `backend/ingestion/extractor.py:333-345`, no `response_format` / `format=` parameter in any adapter).
3. Add function / tool-calling support to `GenerationRequest` and adapters — `LlmClientProtocol` `TODO(production)` flags "Add tool/function calling support in GenerationRequest"; `GenerationRequest` has no `tools` / `tool_choice` field, adapters do not pass tools to OpenAI `chat.completions.create` or Anthropic `messages.create`, and the §14.1 agent-framework recommendation calls out tool-use as the trigger for adopting LangGraph (`backend/llm/adapters/protocols.py:14-21`, `backend/llm/models.py:52-66`, `docs/architecture.md:1344`).
4. Add a prompt template registry with versioning, storage, and audit — Prompts live as hard-coded strings scattered across modules (`_DEFAULT_SYSTEM_PROMPT` in `_rag_bridges.py:34-37`, `_build_prompt` in `extractor.py:318-346`), `service_models.PromptTemplate` exists only as a request-shape with `.format()` rendering and no `id` / `version` / `checksum`, and `LlmCompletionReference` does not record which template version produced a completion (`backend/llm/service_models.py:32-43`, `backend/llm/service.py:96-107`, `backend/events/types.py:202-213`).
5. Add a response cache for deterministic / repeatable prompts — `LlmService.generate` always invokes the adapter and there is no content-hash / `(model, messages, temperature)` cache anywhere in `backend/llm/`; deterministic extraction (`temperature=0.1`) and identical RAG follow-ups repay full provider cost on every call (`backend/llm/service.py:30-67`, `backend/ingestion/extractor.py:270-284`).
6. Replace the `_CHAR_PER_TOKEN=4` heuristic with provider-aware token counting and a context-window budget enforcer — `_fit_context_to_budget` and `LlmClientProtocol` `TODO(production)` both flag the missing `count_tokens(request)` surface; over-budget prompts are silently truncated by character heuristic, with no per-model context-length registry, and the service-level `TODO(production)` calls out missing pre-flight token budget checking and a model-capability registry (`backend/api/_rag_bridges.py:38-39`, `backend/api/_rag_bridges.py:341-360`, `backend/llm/adapters/protocols.py:14-21`, `backend/llm/service.py:19-24`).
7. Add long-context summarization / chunked-reduce strategy for over-window inputs — When `_fit_context_to_budget` would drop context, the system silently truncates instead of map-reducing; no `summarize_context` / hierarchical-summary path exists in `rag/` or `llm/`, and the §14.1 recommendation to evaluate LangGraph notes branching/tool-use as the trigger (`backend/api/_rag_bridges.py:341-360`, no summarization helper in `backend/rag/service.py`).
8. Add per-provider cost tracking and a cost-attribution surface — `CompletionMetadata` captures token counts but no `cost_usd` / `pricing_table` / per-tenant / per-KB roll-up exists; `LlmCompletionReference` exposes `completion_length` but not tokens or cost; Ollama and in-memory adapters do not even capture token counts (`backend/llm/models.py:40-49`, `backend/llm/adapters/ollama_adapter.py:65-74`, `backend/llm/adapters/in_memory.py:30-40`, `backend/events/types.py:202-213`).
9. Add LLM observability — per-adapter latency, token counts, error class, retry-attempt counts, fallback-hop counts — `LlmService` and adapters emit no metrics, traces, or structured logs beyond `fallback.py` logging a warning per failed hop and `factory.py` logging skipped providers; per-provider latency, p95s, retry-budget consumption, and circuit-breaker state are invisible (`backend/llm/service.py:30-79`, `backend/llm/adapters/openai_adapter.py:103-129`, `backend/llm/adapters/anthropic_adapter.py:103-131`, `backend/llm/adapters/fallback.py:31-47`).
10. Harden fallback-chain robustness with timeouts, retry budgets, and a circuit breaker — `FallbackLlmClient` only catches `LlmProviderError`; bare `Exception` from a non-rate-limit provider failure becomes `LlmProviderError` after wrapping, but there is no per-adapter request timeout (Ollama is the only adapter with `timeout_seconds=60.0` configured on the httpx client, OpenAI / Anthropic SDK clients use library defaults), no chain-level deadline, no per-provider retry budget, and no circuit-breaker that opens after N consecutive failures so a flapping primary keeps paying its retry tax on every request (`backend/llm/adapters/fallback.py:31-47`, `backend/llm/adapters/openai_adapter.py:56-77`, `backend/llm/adapters/anthropic_adapter.py:56-77`, `backend/llm/adapters/ollama_adapter.py:18-25`).
11. Add per-provider rate-limit configuration (RPM / TPM) and a request-side throttle — OpenAI / Anthropic adapters only react to 429s with exponential backoff; there is no token-bucket / leaky-bucket throttle in front of the adapter, no `LlmConfig.requests_per_minute` knob, and burst extraction during ingestion will spam 429s instead of pre-throttling (`backend/llm/adapters/openai_adapter.py:103-129`, `backend/llm/adapters/anthropic_adapter.py:103-131`, `backend/config/schema.py:116-125`).
12. Add a vLLM adapter (§14.2 roadmap) — `architecture.md` lists vLLM as a supported self-hosted backend (`docs/architecture.md:126,138,1325`) but `LlmConfig.provider` `Literal["openai", "anthropic", "local", "ollama"]` has no `vllm` value, `factory.py:_instantiate_provider` has no `vllm` branch, and `backend/llm/adapters/` has no `vllm_adapter.py`; per the architecture rule, the Literal must not be widened until the adapter and factory wiring exist (`backend/config/schema.py:119`, `backend/llm/factory.py:95-133`).
13. Add a multi-model router that picks the right provider/model per task class — `LlmConfig` carries a single `provider` / `model`, the worker `build_llm_client(config)` constructs one client per process, and `GenerateRequest.model_name` is plumbed through but ignored by `OpenAILlmClient` / `AnthropicLlmClient` which use `self._model_name` from config; there is no "cheap model for short prompts, expensive model for long reasoning" routing or per-capability registry (`backend/config/schema.py:116-125`, `backend/agent/coordinator.py:594-600`, `backend/llm/adapters/openai_adapter.py:65,79-101`, `backend/llm/adapters/anthropic_adapter.py:65,79-101`).

Add prompt-injection defense and PII redaction for user-supplied content reaching the LLM — RAG chat passes `request.question` and retrieved context items straight into the prompt with only a `system_prompt` instruction and no allow-list / delimiter-escape / "ignore prior instructions" stripping; ingestion passes raw chunk text including any embedded prompt-shaped strings; no sanitizer module exists in `backend/llm/` or `backend/shared/` (`backend/api/_rag_bridges.py:240-275`, `backend/ingestion/extractor.py:270-284`).
15. ### Open questions
- Should `stream_generate` be `async` (current `LlmServiceProtocol.generate_stream` signature) or sync iterator (current `LlmClientProtocol` would need a parallel sync method, mirroring `RagAnswerGenerator.stream_generate`)? The rag bridge and SSE writer are sync today; flipping to async would propagate up through `RagService.stream_answer` and `api/routers/rag.py:_stream_sse`.
- Should JSON-mode be a `GenerationRequest.response_format` field (caller picks per-call) or a `LlmConfig.json_mode` toggle (config-time per-deployment)? The ingestion extractor wants per-call; future tool-use plus JSON-mode combinations argue for per-call.
- Should the prompt template registry live in `backend/llm/prompts/` as a filesystem-backed registry (versioned in git, simple) or in Postgres via `database.ConnectionProvider` (mutable at runtime, auditable, but adds a migration)? The §14.2 audit-log requirement leans Postgres; the prototype velocity leans filesystem.
- Should the response cache be keyed on the full message list (safe, never collides) or on a normalized `(model, system_prompt, user_prompt, temperature)` tuple (higher hit rate, may collide if hidden state matters)? The embeddings module faces the same question — pick once and share.
- Should the model-capability registry be hard-coded in `backend/llm/capabilities.py` (matches embeddings' dimension-table option), discovered at adapter construction via a `health_check()` probe, or pulled from each provider's `/v1/models` endpoint? Hard-coded drifts; probed costs a startup round-trip and assumes the provider exposes capabilities.
- Should the multi-model router be a request-time `model_name` switch (caller picks, similar to `GenerateRequest.model_name` today) or a `task_class` enum (caller declares intent, router picks the model from a policy table)? The latter decouples callers from provider model identifiers but introduces a policy-config surface.
- Does the circuit-breaker open per-`(provider, model)` or per-`provider` regardless of model? OpenAI 5xx on `gpt-4o` does not necessarily imply `gpt-4o-mini` is unhealthy; per-`(provider, model)` is finer-grained but multiplies state.
- Should prompt-injection defense reject suspicious content (hard fail with a `LlmConfigurationError`) or sanitize and continue (silent strip with a metric counter)? Reject blocks legitimate edge cases (a Medicare policy doc that quotes "Ignore prior instructions"); sanitize risks under-blocking. RAG and ingestion may want different policies.
