## File: docs/backlog/events.md

**Scope:** The Redis Streams-backed event bus abstraction (`backend/events/`) — `EventBus` protocol, in-memory and Redis Streams adapters, typed event envelope (`EventBase` + `AnyEvent` union), serialization codec, runtime/factory wiring, dead-letter routing, consumer group management, and the documented event catalog (`docs/ledger/event-catalog.md`). Covers the architectural commitments in `docs/architecture.md` §4 (communication patterns), §5.2 (events module), and §11.3 (trace-ID propagation across stream events).

### Epics
1. Reclaim stale pending entries with XPENDING/XCLAIM in the Redis adapter — `events/adapters/redis_streams.py:99` carries a `TODO(production)` for "XPENDING/XCLAIM for reprocessing stale messages"; `EventBus.consume` only does `XREADGROUP ">"` (`redis_streams.py:72`), so if a worker crashes mid-handler the delivery stays pending forever and no replacement consumer reclaims it.
2. Trim Redis streams with a MAXLEN/XTRIM retention policy — `events/adapters/redis_streams.py:38` documents the gap as a `TODO` ("Add MAXLEN/XTRIM to prevent unbounded stream growth"); `publish()` uses `xadd` with no cap, so every event type's stream grows without bound and ops have no retention contract.
3. Version the event envelope and enforce compatibility rules — `EventBase.schema_version: int = 1` exists (`events/types.py:20`) and `tests/events/test_types.py:68` round-trips a `schema_version=2` payload, but `codec.decode_event` never reads/validates it (`events/codec.py:87`) and there is no documented compatibility policy (additive vs. breaking, when to bump, registry-per-version) — `codec.py:46` flags the gap explicitly.
4. Auto-register event subclasses in EVENT_TYPE_REGISTRY — `EVENT_TYPE_REGISTRY` in `events/codec.py:43` is hand-maintained (one line per event type); the same TODO note at `codec.py:46` calls for "auto-discovery from `EventBase` subclasses (use `__init_subclass__` or a class decorator)" — every new event today requires editing both `types.py` and `codec.py` plus the `AnyEvent` union or it silently fails to deserialize.
5. Propagate W3C Trace Context across stream events — `EventBase` carries only `correlation_id` (`events/types.py:14-20`); `shared/tracing.py` has no inject/extract helpers and `codec.encode_event` (`events/codec.py:79`) emits only `event_type` + `event_body`. Architecture §11.3 requires "trace ID embedded in event metadata" so producer spans link to consumer spans; this is a cross-edge to `_observability.md`.
6. Wire publisher retry/backoff and connection health on the Redis adapter — `RedisStreamsEventBus.publish` is a bare `xadd` with no retry, no timeout, no backoff (`events/adapters/redis_streams.py:36`); the `TODO(production)` at line 37 explicitly lists "connection error handling with retry and backoff" and `runtime.create_event_bus` (`events/runtime.py:48`) does no `PING` health check on startup, so a transient Redis blip drops events from API publishers silently.
7. Make the in-memory adapter mirror Redis Streams semantics for tests — `InMemoryEventBus.ensure_consumer_group` is a no-op (`events/adapters/in_memory.py:37-45`) and the queue model tracks `delivered` per entry but not per consumer group, so integration tests that rely on consumer-group fan-out, pending-list semantics, or stale-claim behaviour cannot exercise those code paths against the in-memory backend; `adapters/in_memory.py:43` carries the TODO.
8. Add a CI check that every produced event is documented in the event catalog — `docs/ledger/event-catalog.md` is hand-maintained against `events/types.py`; nothing in CI guarantees that adding a new `EventBase` subclass updates the catalog, the `EVENT_TYPE_REGISTRY` literal, or the `AnyEvent` union (`events/types.py:410`). A drift check should fail PRs where any of the three diverges or the catalog is out of date.
9. Provide a replay tool for re-processing events from a stream position — there is no script under `scripts/` for replaying Redis stream entries (`XRANGE`/`XREVRANGE` + re-publish or direct handler invocation) for incident debugging or backfill; the only retry path is the in-flight one in `agent/coordinator.py:2345 run_handler_with_retry`, which routes to DLQ rather than replaying earlier events.
10. Implement DLQ replay and operator triage tooling — `EventBus.publish_to_dlq` writes to `<stream>.dlq` (`events/adapters/redis_streams.py:118`) and `agent/coordinator.py:2412` routes there on retry exhaustion, but there is no operator surface to list, inspect, retry, or purge DLQ entries; `tests/events/test_in_memory.py:58` only asserts the write path. Architecture §11.2 references DLQ-rate alerting which presupposes triage tooling exists.
11. Define a tenant-aware stream-naming strategy — `EventBusSettings.stream_name` is `"{prefix}.{event_type}"` with no tenant segment (`events/runtime.py:30-32`); architecture §12.3 promises per-tenant data separation "at the adapter layer", so today every tenant shares one stream per event type with no enforcement. Choose stream-per-tenant vs. tenant-id-on-envelope-with-server-side-filter (cross-edge to `_multitenancy.md`).
12. Specify a multi-region replication strategy for the event bus — Redis Streams is a single-instance Redis primitive; neither `events/runtime.py` nor `docker-compose.dev.yaml` references Redis Sentinel, Redis Cluster, or cross-region replication. Architecture §14.2 lists CI/CD geo-distribution as future work but no equivalent statement exists for the event bus; consumer-group semantics require an explicit choice (Sentinel HA single-region vs. active-active via Redpanda/Kafka migration vs. accept single-region).
13. Document and codify producer delivery guarantees — `RedisStreamsEventBus.publish` returns the `xadd` message ID but has no confirmation hook, no `WAIT`/replication acknowledgement, and the in-memory adapter returns a synthetic ID (`events/adapters/in_memory.py:30-35`); the codebase has no "at-least-once vs. at-most-once" statement and `docs/ledger/event-catalog.md` does not capture per-event delivery expectations. Pair with epic 6 (publisher retry) to settle the guarantee story end-to-end.
14. Add idempotency-key support to the event envelope — handlers in `agent/coordinator.py` rely on downstream upsert keys (e.g., raw_records `content_hash`, `(entity_id, metric_name, observed_at)`) for replay safety; there is no envelope-level `idempotency_key` field on `EventBase` (`events/types.py:14-20`) and no per-event-type dedup table for handlers that are not naturally idempotent. The monitoring dedup window (`monitoring/service.py:79`) operates on alert candidates, not on raw event deliveries, so a re-delivered `RiskScoredEvent` can still double-write rows in the absence of upsert semantics.

### Provisional cross-file edges
- Reclaim stale pending entries with XPENDING/XCLAIM in the Redis adapter unblocks the worker shutdown/restart story tracked in `agent.md` — graceful shutdown must hand off, not lose, pending entries.
- Propagate W3C Trace Context across stream events depends on `_observability.md` — `shared/tracing.py` must expose `inject`/`extract` helpers before the codec can serialize the headers.
- Define a tenant-aware stream-naming strategy depends on tenant-scope plumbing in `_multitenancy.md` — the tenant ID source must exist before the stream name (or envelope) can carry it; downstream fan-out into `monitoring.md`, `records.md`, and `knowledgebases.md` to keep publishers tenant-aware.
- Implement DLQ replay and operator triage tooling has fan-out into `api.md` (an admin-only triage endpoint) and `frontend.md` (a small ops panel) and depends on `_security.md` for admin RBAC scoping.
- Add a CI check that every produced event is documented in the event catalog depends on `_cicd.md` — the check ships as a CI step alongside the backlog-consistency hook in `docs/superpowers/specs/2026-05-24-complete-backlog-design.md` §8.
- Specify a multi-region replication strategy for the event bus depends on `_infra.md` — Redis HA/cluster manifests, Sentinel topology, or substrate migration (Redpanda/Kafka) live in the infra epic.
- Trim Redis streams with a MAXLEN/XTRIM retention policy has a cross-edge to `_observability.md` — the chosen retention bound must be observable (stream length gauge, trim event counter) and to `database.md`/`storage.md` for any persisted projection that must outlive the trimmed stream.
- Add idempotency-key support to the event envelope has fan-out into `monitoring.md` (alert handler dedup), `analytics.md` (risk/explainability handlers), and `agent.md` (`run_handler_with_retry` retry surface in `agent/coordinator.py:2345`).

### Open questions
- Stream-per-tenant vs. envelope-tenant-id-with-filter — stream-per-tenant scales operationally with tenant count but multiplies consumer groups; envelope-with-filter keeps one stream per event type but pushes the isolation gate into every handler. Need a decision before epic 11 can produce concrete stories.
- Whether to stay on Redis Streams long-term or migrate to a Kafka-compatible substrate (Redpanda, Warpstream, Kafka) for multi-region and at-least-once-with-replication. Architecture §13 locks "Redis 7+ Streams" today; epic 12 forces this question.
- Whether `correlation_id` (already on `EventBase` at `events/types.py:17`) and the W3C `trace_id` from epic 5 should be unified or remain parallel identifiers — same open question lives in `_observability.md`; resolving it once changes both files.
- Whether DLQ entries should be Postgres-backed (queryable, joinable to workflow runs) instead of Redis-backed (`<stream>.dlq` at `events/adapters/redis_streams.py:120`) — affects epic 10 storage substrate and any cross-edge to `database.md`.
- Whether the event catalog drift check (epic 8) is a Python script consumed by CI or a `pytest` collection test — either works; the choice affects where the story lands (scripts/ vs. tests/).
- Whether epic 14's idempotency keys live on `EventBase` (envelope) or per event-type as named fields — envelope is uniform but adds noise to events that are already idempotent by domain key; per-type is precise but requires per-handler wiring.
