## File: docs/backlog/_plugins.md

**Scope:** Define and deliver the third-party plugin system called out by `docs/architecture.md` §14.2 (priority Low — "after architecture stabilizes"). Today the repo has **no plugin SPI, no discovery mechanism, no plugin lifecycle, and no sandboxing**: every analytics capability ships in-tree under `backend/analytics/<capability>/`, every adapter is wired by hand in `backend/api/dependencies.py` (`get_risk_service`, `get_gnn_service`, `get_timeseries_service`, etc.), and `DomainConfig` (`backend/config/schema.py:49 CapabilitiesConfig`, `backend/config/schema.py:189 AnalyticsConfig`) has fixed Literal feature flags. The only "pluggable" seams that exist are protocol-typed constructor parameters such as `RiskScoringStrategyProtocol` (`backend/analytics/risk/protocols.py:25`), `DetectionStrategy` in timeseries (`backend/analytics/timeseries/service.py:17`), and the `[project.optional-dependencies]` extras list in `backend/pyproject.toml:22` — these are protocol shapes a future plugin SPI can adopt, not a plugin system. Frontend has no plugin or extension scaffolding (`grep -rn 'plugin' chili_app/src` returns only filename-extension references). This concern is essentially greenfield and is gated behind the §2.1/§2.2/§2.4 principles (vendor-agnostic protocols, narrow module boundaries, interface-first design) — plugins must slot into those seams, not bypass them.

### Epics
1. Define the plugin SPI — the set of capability protocols a third party may implement — `Nothing exists yet`: there is no top-level `plugins/` package and no `PluginProtocol`. The SPI must enumerate which seams are pluggable in v1 (analytics strategies via `RiskScoringStrategyProtocol`/`DetectionStrategy`, analytics services via `RiskServiceProtocol`/`GnnServiceProtocol`/`TimeseriesServiceProtocol`, custom indicators/feature extractors, custom monitoring rules, custom RAG retrievers via `rag` protocols, custom record-feed mappers under `backend/records/`), which are explicitly out-of-scope for v1 (storage/graph/vector/LLM adapters — those remain in-tree per §2.1), and the FastAPI router-contribution shape (plugin-supplied `APIRouter` mounted under a reserved `/plugins/{plugin_id}/...` prefix).
2. Implement plugin discovery and loading — `Nothing exists yet`: `backend/api/app.py:142-156` hand-includes every router and `backend/api/dependencies.py` hand-imports every adapter. Pick one of (a) `importlib.metadata` entry-points under a `chiliai.plugins` group, (b) a `plugins:` list in `DomainConfig` enumerating import paths, or (c) a filesystem scan of `$CHILI_PLUGIN_DIR`; build a `PluginRegistry` in a new `backend/plugins/` package that loads, validates, and exposes discovered plugins to `create_app()` and to `agent.coordinator`; decision recorded in spec, with both backend service registration and `app.include_router(...)` extension points wired.
3. Add a plugin manifest format and load-time validation — `Nothing exists yet`: each plugin must ship a `chiliai_plugin.toml` (or `pyproject.toml [tool.chiliai.plugin]` block) declaring `id`, `name`, `version`, `chiliai_api_version` (semver range), `capabilities` (which SPI protocols it implements), `permissions` (declared capability scopes — graph_read, graph_write, vector_read, llm_invoke, event_publish, http_outbound, fs_read, fs_write — cross-edge to Epic 5), `config_schema` (Pydantic-importable path for plugin-local config), and `entry_points`; manifest parsed and validated by the `PluginRegistry` before any plugin code is imported, with a defined human-readable error format for each failure mode.
4. Define plugin lifecycle and admin operations — `Nothing exists yet`: there is no install/enable/disable/uninstall flow and no `/plugins/*` router (see `backend/api/routers/` listing). Specify the lifecycle states (`discovered → loaded → enabled → disabled → unloaded`), define `PluginProtocol.startup(context)` and `PluginProtocol.shutdown()` hooks, decide whether enable/disable is hot (per-process, no restart) or cold (config change + restart) for v1, and ship `GET/POST /plugins`, `POST /plugins/{id}/enable`, `POST /plugins/{id}/disable`, `DELETE /plugins/{id}` admin routes guarded by an `admin`-tier `require_role` (cross-edge to `_security.md` Epic 11).
5. Enforce plugin sandboxing and capability declarations — `Nothing exists yet`: there is no security boundary today (an in-tree plugin would run with full process privileges). Decide and ship the v1 sandboxing posture: at minimum, manifest-declared `permissions` are enforced at the SPI surface (graph adapter passed to the plugin only honors declared scopes; `event_publish` rejected if undeclared; outbound HTTP gated by an allowlist), with sandboxed-subprocess or WASI-style isolation deferred to a later epic. Cross-edge to `_security.md` for trust model, signing, and supply-chain controls.
6. Establish plugin versioning and the compatibility matrix — `Nothing exists yet`: there is no public `chiliai_api_version` constant. Define and publish the host platform's SPI version (semver, decoupled from `backend.pyproject.toml:3 version`), make the `PluginRegistry` reject manifests whose `chiliai_api_version` range does not include the host SPI version, document the deprecation policy (one-minor-version warning before SPI-breaking changes), and add a compatibility matrix doc enumerating supported plugin API versions per host release.
7. Ship a plugin testing harness — `Nothing exists yet`: today a third-party `RiskScoringStrategyProtocol` impl has no published way to exercise host wiring. Provide a `chiliai.testing` (or `backend/plugins/testing/`) package exposing `PluginTestHarness` that loads a single plugin against an in-memory host (in-memory graph/vector/embedding/LLM/storage/event-bus adapters), a pytest fixture set, manifest-conformance tests, and a `chiliai plugin verify` CLI command that runs them. Ship a worked example plugin (a no-op `RiskScoringStrategy`) and its test suite to anchor the contract.
8. Define the plugin documentation contract — `Nothing exists yet`: there is no docs spec for what a plugin must ship. Specify the minimum doc set (`README.md` with capability summary, install instructions, declared permissions and rationale, config-schema description, version compatibility statement; `CHANGELOG.md` keyed to plugin version; optional `examples/`), publish a template plugin repo, and add a `chiliai plugin lint` CLI step (folded into Epic 7's harness) that fails on missing doc files.
9. Dogfood: migrate one in-tree analytics sub-package behind the plugin SPI — `backend/analytics/risk/` is the natural pilot because `RiskScoringStrategyProtocol` (`backend/analytics/risk/protocols.py:25`) is already a protocol-shaped strategy seam, while leaving `backend/analytics/risk/service.py` in-tree as the host-side service. Extract `LinearScoringStrategy` (`backend/analytics/risk/adapters/linear_strategy.py`) into a first-party plugin loaded through the registry; prove the SPI end-to-end without changing public API behavior; keep an in-tree fallback for the case where no plugin is enabled. Defer migrating gnn/timeseries/explainability until v1 SPI is shaken out.
10. Wire plugin observability into the host telemetry pipeline — `Nothing exists yet`: a third-party plugin today would have no defined logging/metrics/tracing surface. The SPI's `PluginContext` must inject a scoped `structlog.BoundLogger` (tagged `plugin_id`, `plugin_version`), a Prometheus metric registry with a `chiliai_plugin_*` namespace, and an OpenTelemetry tracer; host emits per-plugin `plugin_call_total{plugin_id,result}` and `plugin_call_latency_seconds{plugin_id}` around every SPI dispatch; uncaught plugin exceptions logged with manifest provenance and never crash the host. Cross-edge to `_observability.md` for sink wiring.
11. Surface plugin configuration in `DomainConfig` — today `CapabilitiesConfig` (`backend/config/schema.py:49`) and `AnalyticsConfig` (`backend/config/schema.py:189`) are closed Literal/scalar models with no escape hatch for plugin-supplied config. Add a `plugins: dict[str, PluginConfig]` field (or `PluginsConfig` sub-model) where each entry carries `enabled: bool`, `version_constraint: str`, and a typed `settings: BaseModel` validated against the plugin's declared `config_schema` at load time; ensure `config/loader.py` resolves plugin-config validation after plugin discovery so unknown plugins produce a clear error. Cross-edge to `config.md`.
12. Provide a frontend plugin-widget extension point — `Nothing exists yet` (frontend has no plugin scaffolding, only file-extension references in `useKnowledgeBaseDocuments.ts` and CodeMirror `Extension` in `YamlEditor.tsx`). Define how a plugin contributes UI: choose between (a) plugin-supplied dashboard widgets registered via a host-served `/plugins/{id}/widgets` manifest and rendered in iframes/web-components, (b) plugin-declared API surfaces consumed by host-shipped generic widget components, or (c) explicitly defer UI plugins to v2. Recommend (b) for v1 to avoid frontend bundling/sandboxing complexity; document the constraint that plugin SPI v1 is backend-only.

### Open questions
- **Discovery mechanism**: `importlib.metadata` entry-points (Pythonic, requires `pip install` of plugin), `DomainConfig.plugins[].import_path` (explicit, version-pinned in config), or `$CHILI_PLUGIN_DIR` scan (operator-friendly, weakest provenance)? This is the v1 shape-defining decision and should be settled in Epic 2's spec.
- **SPI surface for v1**: ship analytics strategies only (smallest, already protocol-shaped), or also custom monitoring rules and record-feed mappers (broader, larger SPI surface)? Affects scope of Epic 1, Epic 7, and Epic 9.
- **Hot vs cold enable/disable**: per-process hot-reload (complex, requires careful DI rebuilding in `backend/api/state.py`) or config-change + restart (simple, matches current deploy model)? Affects Epic 4 and Epic 11.
- **Sandboxing posture for v1**: capability-declaration enforcement only (cheap, "trust the publisher"), or genuine isolation via subprocess/WASI (expensive, defers v1)? If isolation is deferred, what is the explicit trust model — first-party plugins only, signed-manifest allowlist, or admin-approved on install? Affects Epic 5 and the cross-edge to `_security.md`.
- **First-party plugin packaging**: when Epic 9 extracts `LinearScoringStrategy` into a plugin, does it ship as its own distributable on PyPI, as an in-repo `backend/plugins_firstparty/` subdir, or live in the dev extras (`backend/pyproject.toml`)? Affects the deployment model and the `_cicd.md` cross-edge.
- **Frontend plugin scope**: defer to v2 explicitly, or commit to option (b) generic widgets reading plugin-declared APIs in v1? If deferred, Epic 12 collapses to a "documented constraint" story.
- **Marketplace / registry**: is there a future "chiliAI plugin marketplace" registry, or is install always direct (pip install / git clone)? Affects long-term shape but should be called out as out-of-scope for v1 to avoid scope creep.
- **Multi-tenant plugin visibility**: in a multi-tenant deployment (cross-edge `_multitenancy.md`), are plugins enabled platform-wide, per-tenant, or both? Affects `DomainConfig` shape in Epic 11 and the admin surface in Epic 4. Recommend deferring — pin v1 to platform-wide enablement, revisit when multi-tenancy lands.
