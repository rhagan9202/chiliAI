## File: docs/backlog/agent.md

**Scope:** Workflow coordinator, worker entry point, run/state lifecycle, retry+DLQ orchestration, workflow run persistence, and operational health/readiness for the agent module (`backend/agent/`) and its API surface (`backend/api/routers/workflows.py`).

### Epics
1. Add async agent service boundary — `AgentServiceProtocol` exposes only sync methods, but `list_workflows` is called from an `async def` FastAPI route; Redis I/O and event-bus publish run on the event loop (`backend/agent/protocols.py:12-31`, `backend/agent/service.py:25-33`, `backend/api/routers/workflows.py:24-39`).
2. Enforce hard cancellation before expensive worker stages — `cancel_workflow` only writes status; the coordinator checks `TERMINAL_RUN_STATUSES` inside `WorkflowEventTracker.begin_event` after dispatch and not before each expensive handler (`backend/agent/service.py:129-138`, `backend/agent/workflow_tracking.py:80-108`).
3. Add indexed workflow lookup by correlation ID — `WorkflowEventTracker._find_by_correlation_id` scans `list_runs(limit=1000)` linearly and has no store-side correlation index (`backend/agent/workflow_tracking.py:194-198`, `backend/agent/adapters/redis_store.py:81-110`).
4. Make workflow store updates race-safe with conditional writes / versioning — `RedisWorkflowRunStore.update_run` does read-modify-write through `save_run`; tracker terminal-status protection is in-process only, so concurrent worker + API updates can overwrite cancellation/completion (`backend/agent/adapters/redis_store.py:112-121`, `backend/agent/models.py:102-113`).
5. Add workflow retention, archival, and idempotency TTL — Redis workflow keys, idempotency keys, and created-at index entries are written without TTL or cleanup hooks, and `WorkflowRunStoreProtocol` exposes no expiry surface (`backend/agent/adapters/redis_store.py:39-72`, `backend/agent/adapters/protocols.py:11-48`).
6. Add audit-grade workflow lifecycle history — `WorkflowRun` is a mutable current-state projection; tracker overwrites status/steps in place with no append-only ledger of submit/begin/complete/fail/cancel/retry/DLQ transitions (`backend/agent/models.py:79-99`, `backend/agent/workflow_tracking.py:99-165`).
7. Add worker leases, heartbeats, and stale-run reconciliation — `HealthState` only tracks last processed event in process memory; runs left `queued`/`running` after a worker crash are not detected or recovered, and there is no worker identity in `WorkerDependencies` (`backend/agent/health.py:22-57`, `backend/agent/coordinator.py:222-251`).
8. Build DLQ inspection, replay, and resolution workflows — `run_handler_with_retry` publishes to DLQ then returns; no agent-owned service or API exposes list/get/replay/resolve/ignore of DLQ entries linked to workflows (`backend/agent/coordinator.py:2345-2413`).
9. Split worker liveness from readiness with dependency probes — `/health` returns process-only status; there is no `/readiness` endpoint and no probe of event bus, run store, graph, vector, embeddings, storage, or DB (`backend/agent/health.py:124-143`, `backend/agent/coordinator.py:2571-2641`).
10. Introduce typed `AgentConfig`/`WorkerConfig` with production guardrails — store backend is selected via env var (`CHILI_WORKFLOW_RUN_STORE_BACKEND`) outside `DomainConfig`; retention, leases, concurrency, DLQ replay, and worker identity have no typed config block, and no guardrail rejects in-memory stores in prod (`backend/agent/adapters/runtime.py:15-32`, `backend/agent/coordinator.py:609-725`).
11. Add store-level indexes and API pagination for workflow listing — Redis `list_runs` reads the entire created-at index and filters in process, and `/workflows` returns a flat list without `has_more`/cursor semantics (`backend/agent/adapters/redis_store.py:81-110`, `backend/api/routers/workflows.py:19-39`).
12. Add stage-level execution policy (per-event timeouts, retry, fatal/retryable taxonomy) — `RetryPolicy` is a single global object applied to every handler, and `handle_risk_scored` / `handle_graph_updated_for_analytics` use ad-hoc `except` blocks rather than declared policy (`backend/agent/models.py:20-32`, `backend/agent/coordinator.py:1429-1475`).
13. Formalize workflow definitions and dependency graph — `WorkflowSubmissionRequest.requested_steps` is `list[str]`; the event→step map and default sequence are hardcoded module constants, and unknown step names are not rejected at submission (`backend/agent/workflow_tracking.py:35-58`, `backend/agent/service.py:37-65`).
14. Add per-stage and per-KB concurrency limits / backpressure — `drain_ingestion_events` processes deliveries sequentially in one loop with no global, per-stage, or per-KB concurrency caps and no queue-depth metrics (`backend/agent/coordinator.py:2416-2570`).
15. Production-harden the Redis workflow store — `RedisWorkflowRunStore.__init__` takes a URL + prefix only; no connect/socket timeouts, retry policy, pool sizing, TLS validation, schema versioning, or `check_health()` surface (`backend/agent/adapters/redis_store.py:19-37`).
16. Enforce RBAC, tenant/KB scoping, and metadata redaction across workflow ops — only `viewer` is enforced for list; cancellation/start/DLQ/history APIs have no policy registry entries, and idempotency keys, user metadata, and downstream error messages are written verbatim to logs (`backend/api/routers/workflows.py:19-39`, `backend/agent/service.py:84-100`).
17. Add workflow metrics, traces, and structured logs at the agent boundary — coordinator uses `observe_pipeline_stage` per stage but emits no agent-owned metrics for submissions, durations, retries, DLQ publishes, cancellations, or recovery; correlation/workflow IDs are not attached to traces from the API submission path (`backend/agent/coordinator.py:154,2402-2412`, `backend/agent/service.py:69-100`).
18. Add a Postgres-backed durable `WorkflowRunStore` adapter — protocol exposes the surface but only `InMemoryWorkflowRunStore` and `RedisWorkflowRunStore` exist; Redis is not authoritative storage for audit-grade lifecycle (`backend/agent/adapters/protocols.py:11-49`, `backend/agent/adapters/runtime.py:15-32`).
19. Add `start_workflow` / `cancel_workflow` / DLQ-replay HTTP endpoints — `backend/api/routers/workflows.py` only mounts `GET /workflows`; analysts cannot submit, cancel, or replay workflows through the API even though `AgentService` supports submit/cancel (`backend/api/routers/workflows.py:1-39`, `backend/agent/service.py:37-138`).
20. Add a production agent quality gate (multi-worker, crash recovery, retention, DLQ replay) — current tests cover unit paths; there is no documented load/concurrency/crash-recovery suite, and prior audit flagged a no-op test class body in `backend/tests/agent/test_coordinator.py` ("Nothing exists yet" for the production-readiness profile).

### Provisional cross-file edges
- Add audit-grade workflow lifecycle history depends on Postgres-backed durable `WorkflowRunStore` adapter — append-only history needs the durable store before the agent ledger can be authoritative.
- Add audit-grade workflow lifecycle history depends on schema migrations in `database.md` — history tables must be created via Alembic.
- Add stage-level execution policy depends on stage timeout/retry contracts in `events.md` — per-stage retry/timeout policy must align with event-bus delivery and DLQ contracts.
- Build DLQ inspection / replay / resolution workflows depends on DLQ read-model surface in `events.md` — the event bus owns DLQ persistence today; the agent needs a read interface before exposing list/replay APIs.
- Split worker liveness from readiness with dependency probes depends on dependency `check_health()` surfaces in `graph.md`, `vectorstore.md`, `embeddings.md`, `storage.md`, `database.md`, and `events.md` — readiness cannot probe what those modules do not expose.
- Add worker leases / heartbeats / stale-run reconciliation depends on consumer-group pending-entry inspection in `events.md` — recovery has to read Redis Streams PEL data through the event bus protocol.
- Add per-stage and per-KB concurrency limits depends on observability primitives in `_observability.md` — queue depth, in-flight, and saturation metrics need a shared metrics surface.
- Add workflow metrics / traces / structured logs depends on the cross-cutting telemetry stack in `_observability.md` — exporter, naming conventions, and tracing setup live there.
- Enforce RBAC / tenant / KB scoping for workflow ops depends on tenant scoping in `_multitenancy.md` and the policy registry in `_security.md` — scope predicates and the route policy registry are owned cross-cutting.
- Add `start_workflow` / `cancel_workflow` / DLQ-replay HTTP endpoints depends on epics in `api.md` — request validation, error mapping, and policy-registry wiring live in the API module.
- Introduce typed `AgentConfig`/`WorkerConfig` depends on `DomainConfig` schema epics in `config.md` — the typed agent/worker section must be added to the shared config schema and loader.
- Add Postgres-backed durable `WorkflowRunStore` adapter depends on `ConnectionProvider` and migration tooling in `database.md` — Postgres adapters in this repo all flow through that provider.
- Add a production agent quality gate depends on multi-worker integration harness in `_cicd.md` — the gate needs a CI profile that runs Redis-backed and multi-worker tests.

### Open questions
- Should durable workflow lifecycle history live in Postgres (consistent with Plan C history tables under `database/`) or remain on Redis with a TTL-bounded archive stream? The 05_17 backlog left both options open and §14.2 audit-log capability points toward Postgres.
- Does workflow cancellation propagate across knowledge bases for `kb.delete`, or is cancellation always scoped to a single workflow run? The current `is_busy` check returns boolean but offers no cascade contract.
- Should `start_workflow` be exposed via HTTP at all, or remain event-bus-only (API publishes `documents.uploaded` etc. and the worker creates fallback runs)? Today `AgentService.start_workflow` exists but no router mounts it.
