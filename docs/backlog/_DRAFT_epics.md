## File: docs/backlog/_cicd.md

**Scope:** CI/CD pipeline — quality gates, container delivery, environment promotion, release automation.

### Epics
- **_cicd.01** — Enforce frontend coverage gate at ≥85% parity with backend — - **Gap:** `ci.yml` runs `npm run test:run` but never invokes vitest `--coverage`, even though `@vitest/coverage-v8` is in devDependencies. No threshold enforced; frontend has no coverage floor while backend gates at 85%. - **Edges (provisional):** none.
- **_cicd.02** — Tighten pyright strict scope and fail CI on scope regressions — - **Gap:** `ci.yml` calls `pyright` without arguments by design (relies on `tool.pyright.include`); there is no audit step that flags new modules added to the tree but not added to `include`, so untyped code silently bypasses the gate. - **Edges (provisional):** none.
- **_cicd.03** — Promote pip-audit and npm audit from soft to hard fail with allow-list — - **Gap:** `ci.yml` pip-audit step uses `… || pip-audit --skip-editable` (a retry that masks real failures); `--ignore-vuln GHSA-0000-0000-0000` is a placeholder. No vulnerability allow-list governance file. npm audit runs but has no allow-list either. - **Edges (provisional):** none.

## File: docs/backlog/_infra.md

**Scope:** Container images, Docker Compose, Kubernetes manifests, Helm chart, cloud IaC, network policy, persistent volumes, ingress/TLS, image registry/promotion, backup/restore, scaling, hybrid deployment.

### Epics
- **_infra.01** — Harden backend and frontend Docker images. — Add non-root `USER`, distroless or `slim`-pinned base by digest, `.dockerignore`, multi-platform builds, SBOM emission, and an image-scan CI hook — current `backend/Dockerfile` and `chili_app/Dockerfile` run as root and pull bases by tag only.
- **_infra.02** — Collapse flat-manifest / Helm duplication. — Either generate `infra/k8s/*.yaml` from `helm template` or delete the flat tree, removing the drift surface between `infra/k8s/` and `infra/helm/chili/templates/`.
- **_infra.03** — Tighten pod-level security across the chart. — Set `readOnlyRootFilesystem: true` (with `emptyDir` for writable paths), drop `runAsNonRoot: false` on the `chili-app` Deployment, add namespace-level PodSecurity admission labels, per-component PodDisruptionBudgets, and PriorityClasses for api/worker.
- **_infra.04** — Add default-deny NetworkPolicies and a service-mesh decision. — No NetworkPolicy exists today; define ingress/egress allow-lists per component (api↔redis/neo4j/qdrant/minio/postgres, worker↔same, app↔api) and decide whether Linkerd/Istio is in scope or NetworkPolicy alone suffices.
- **_infra.05** — Per-environment Helm values and chart-test CI. — Only `values.yaml` and `values-prod.yaml` exist; add `values-staging.yaml` (and a dev-cluster variant), wire `helm lint`, `helm template --validate`, and `chart-testing` into CI so manifest regressions fail PRs.
- **_infra.06** — Production persistent-volume strategy for stateful services. — Define StorageClass, PVC sizing, retention reclaim policy, and snapshot schedules for Neo4j, Qdrant, MinIO, and Postgres in self-hosted mode — currently only Redis has a 5 Gi PVC with no `storageClassName`.
- **_infra.07** — Wire ingress-level TLS by default and finish the nginx-TLS path. — Flat `infra/k8s/ingress.yaml` has TLS commented out, and the `chili-app` image does not bake `nginx-tls.conf`; either ConfigMap-mount the TLS variant or make the image select it at runtime, then make `tls.enabled: true` the chart default for any non-dev profile.
- **_infra.08** — Externalize secrets via External Secrets Operator or CSI driver. — Today, `chili-secrets` is created with `kubectl create secret` and manually rotated; add ESO/CSI templates per cloud provider (AWS Secrets Manager, GCP Secret Manager, Azure Key Vault, Vault) and document rotation cadence. (Cross-edge: `_security.md`.)
- **_infra.09** — Stand up cloud IaC modules (Terraform). — Greenfield: pick Terraform (Pulumi as alternative), create `infra/terraform/{aws,gcp,azure}/` modules covering VPC, EKS/GKE/AKS, managed Redis (ElastiCache / Memorystore / Azure Cache), object storage (S3 / GCS / Blob), DNS, ACM/Cert Manager DNS-01, and IAM bindings consumed by Workload Identity / IRSA.
- **_infra.10** — Container registry, image promotion, signing, and SBOM. — Decide registry (GHCR vs ECR/GAR/ACR), publish multi-arch images per push to `main`, sign with cosign, publish SBOM (CycloneDX/SPDX), enforce immutable tags, and add a `promote` GitHub Action that retags `:edge` → `:rcN` → `:vX.Y.Z`. (Cross-edge: `_cicd.md`.)
- **_infra.11** — Custom-metrics HPA for the worker via KEDA. — CPU is a coarse proxy; install KEDA and replace the worker HPA with a `ScaledObject` that scales on Redis Stream pending-message depth per consumer group (already flagged as future work in `infra/README.md`).
- **_infra.12** — Hybrid / on-prem deployment bundle. — Add an opt-in "self-hosted infra" Helm subchart family (Neo4j, Qdrant, MinIO, Postgres with TimescaleDB) plus air-gapped image-mirror instructions so §10.5's "same images, managed or self-hosted" story actually works end-to-end.
- **_infra.13** — Backup, restore, and disaster-recovery drills for stateful services. — Add CronJobs (or Velero hooks) for Neo4j dumps, Qdrant snapshots, MinIO bucket replication, Postgres `pg_basebackup` / continuous archiving, and Redis AOF/RDB; document and rehearse a restore runbook. (Cross-edge: `_cicd.md`.)
- **_infra.14** — Ship a baseline observability stack with the chart. — Optional dependency on `kube-prometheus-stack` + an OTLP collector + Grafana dashboards/alerts wired to `/metrics` endpoints so the §11 observability spec is reachable from a single `helm install`. (Cross-edge: `_observability.md`.)

## File: docs/backlog/_multitenancy.md

**Scope:** Greenfield introduction of tenant isolation across identity, configuration, persistence, graph/vector/object adapters, KBs, event streams, workflow context, frontend, and quality gates — per `docs/architecture.md` §12.3 and §14.2.

### Epics
- **_multitenancy.01** — Define the tenant identity model in `shared/types.py` — Nothing exists yet; no `Tenant`, `TenantId`, or `tenant_id` field exists anywhere in `backend/shared/` (verified by repo-wide grep). Needs greenfield type plus a `tenant_id` field on `User` (`backend/api/middleware/auth.py:52`), `KnowledgeBase`, `Alert`, and `EvidencePack`.
- **_multitenancy.02** — Extend `DomainConfig` with a tenant binding and per-tenant overrides — Nothing exists yet; `backend/config/schema.py` has no tenant-related class and `CHILI_CONFIG_PATH` (`backend/config/loader.py:51`) loads a single global config. Architecture §9 calls config per-domain but endgame requires per-tenant config selection/overrides.
- **_multitenancy.03** — Resolve tenant context from the JWT claim in API middleware — Nothing exists yet; `User` model at `backend/api/middleware/auth.py:52` only carries `user_id`, `roles`, `email`. No tenant claim is read, validated, or rejected.
- **_multitenancy.04** — Add tenant-scoped DI/request context — Nothing exists yet; `backend/api/dependencies.py` has zero tenant references. Need a `get_current_tenant()` dependency, contextvar propagation, and an unauthenticated-tenant default-deny policy.
- **_multitenancy.05** — Add `tenant_id` columns + composite indexes to every Postgres table — Nothing exists yet; `backend/database/migrations/versions/0001_persistence_baseline.py` keys all tables (raw_records, observations, entity_metric_history, entity_metrics_current, …) on `knowledge_base_id` only. Need a migration that adds `tenant_id` to every table and to the primary/composite keys + indexes.
- **_multitenancy.06** — Enforce tenant scoping in every Postgres query path — Nothing exists yet; depends on Epic 5. Repository/query layer must inject `WHERE tenant_id = :tenant` on every read and write; pyright-level guards against unscoped queries.
- **_multitenancy.07** — Isolate graphs per tenant — Nothing exists yet; `backend/graph/adapters/neo4j_adapter.py:143-164` scopes constraints/indexes/transactions on `knowledge_base_id` against a single shared Neo4j database. Decide between per-tenant Neo4j databases vs. strict `(tenant_id, knowledge_base_id)` label/property scoping and implement.
- **_multitenancy.08** — Isolate vector collections per tenant — Nothing exists yet; `backend/vectorstore/adapters/qdrant_adapter.py:224` and `in_memory.py:105` namespace solely on `knowledge_base_id`. Need per-tenant collection naming (e.g. `t_{tenant}__kb_{kb}`) in both protocol and adapters.
- **_multitenancy.09** — Isolate object-store prefixes per tenant — Nothing exists yet; `backend/storage/adapters/s3_adapter.py:80,199` and `local_fs_adapter.py:31` use a single `base_path` (the only repo reference to "tenants/" is a hard-coded string in `backend/tests/api/test_dependencies.py:257`). Need per-tenant prefix injection at adapter construction or per-write.
- **_multitenancy.10** — Scope KnowledgeBase records and operations by tenant — Nothing exists yet; `backend/knowledgebases/models.py` has no `tenant_id`, `backend/shared/kb_scope.py` resolves scope from `DomainConfig` only. Cross-tenant KB resolution is currently possible by ID guessing.
- **_multitenancy.11** — Scope Redis Stream names and consumer groups by tenant — Nothing exists yet; `backend/events/adapters/redis_streams.py:46-106` uses caller-provided stream/group names with no tenant prefixing. Need a stream-naming policy (e.g. `t.{tenant}.<stream>`) and consumer-group convention to prevent cross-tenant event leakage.
- **_multitenancy.12** — Propagate tenant context through the agent coordinator and workflow envelopes — Nothing exists yet; `backend/agent/coordinator.py` has zero tenant references and event envelopes do not carry tenant. Every workflow step must receive, validate, and forward the originating tenant.
- **_multitenancy.13** — Per-tenant configuration loading and switching — Nothing exists yet; `backend/config/loader.py:20` loads a single config from `CHILI_CONFIG_PATH`. Need a per-tenant resolver, cache, and reload policy (likely depends on Epic 2).
- **_multitenancy.14** — Frontend tenant context, switcher, and API plumbing — Nothing exists yet; `chili_app/src/` has no tenant references (only `workspace-update` SSE event and CSS class names). Need a current-tenant store, header injection on every API call, switcher UI, and tenant gating in the SPA shell.
- **_multitenancy.15** — Cross-tenant query prevention as a hard quality gate — Nothing exists yet; no test in `backend/tests/` exercises tenant isolation. Need adapter-level and end-to-end tests that two tenants cannot read each other's KBs, graphs, vectors, blobs, streams, alerts, or workflows; CI must fail on any leak.
- **_multitenancy.16** — Per-tenant capacity, quotas, and rate limits — Nothing exists yet; rate-limiting is itself flagged as deferred in `docs/architecture.md` §12.4. Endgame multi-tenancy needs per-tenant rate limits and storage/compute quotas to prevent noisy-neighbor abuse.

- **_observability.11** — Integrate frontend error tracking and Web Vitals (Sentry/equivalent) — `chili_app/` has no Sentry/Datadog dependency and the only handler is the stub `ErrorBoundary` at `chili_app/src/components/common/ErrorBoundary.tsx:24` that just `console.error`s; arch §11.4 calls for Sentry and §13 lists it as the production-hardening front-end stack.

- **api.04** — Wire the policy-intelligence store to a durable repository — `/policy/gaps`, `/policy/gaps/{id}`, `/policy/gaps/{id}/cases`, `/policy/briefs` (`backend/api/routers/policy.py`) read and write to `ApiState._policy_gaps` (`backend/api/state.py:194`) with no persistence, no audit history, and no link to the real analytics or KB lifecycle.
- **api.05** — Bridge the WebSocket hub to the Redis Streams event bus — `backend/api/routers/ws.py:4-7,89` documents the gap explicitly (`The actual bridge between the event bus (Redis Streams) and this hub is wired in Epic 8 — for now the hub accepts direct broadcast calls`); `WebSocketHub.broadcast` (`backend/api/routers/ws.py:118-134`) is process-local, so `/ws/alerts` and `/ws/pipeline` subscribers only receive events produced inside the same API process and only when test code or future bridge code calls `hub.broadcast(...)`. Coordinator-published `AlertCreatedEvent` / pipeline-stage events never reach connected SPAs.
- **api.06** — Add WebSocket hub resilience and observability — beyond the missing Redis bridge, `WebSocketHub` keeps connections in a per-process `dict` with no per-connection backpressure, no slow-consumer eviction beyond `WebSocketDisconnect`/`RuntimeError` catches (`backend/api/routers/ws.py:131-134`), no max-clients cap, no metrics (`prometheus_client` counters in `backend/api/middleware/metrics.py:29` track only HTTP), no idle timeout beyond the 30 s ping (`backend/api/routers/ws.py:36`), and the `subscribe` filter is silently dropped on `ValidationError` (`backend/api/routers/ws.py:169-170,183-184`) without acking back to the client.
- **api.07** — Replace the SSE polling loop with event-driven push and add reconnect semantics — `backend/api/routers/events.py:30-52` polls every 5 seconds (`await asyncio.sleep(5)`) and rebuilds the snapshot by calling `repository.list(limit=500)` + `agent_service.list_workflows(limit=500)` + `repository.count_active_alerts(...)` on every tick; there is no event-driven trigger, no Last-Event-ID resume / SSE `id:` field on yielded events (`backend/api/routers/events.py:50`), no per-client cap, and the only `max_events` knob is for tests (`backend/api/routers/events.py:41-42,56`).
- **api.08** — Standardize the API error envelope across all routers — error responses are inconsistent: some routes raise `HTTPException(detail=str)` (`backend/api/routers/knowledgebases.py:158-161,193-195`, `backend/api/routers/alerts.py:46-49`), one route returns a 207 Multi-Status body shaped `{knowledge_base_id, pending_cleanup, steps[]}` (`backend/api/routers/knowledgebases.py:234-241`), KB busy errors map `KbBusyError → 409 detail=str(exc)` (`backend/api/routers/knowledgebases.py:200-204`), records routes funnel three exception classes to three different status codes (`backend/api/routers/records.py:95-107`), and mutations get a separate `ApiEnvelope{status,message}` model (`backend/api/contracts.py:11-15`). There is no `Problem+JSON` (RFC 7807) shape, no `error_code` field, no `correlation_id` echoed back, no `request_id`, and Pydantic 422 bodies still use FastAPI's default loc/msg/type shape.
- **api.09** — Adopt a single Pydantic v2 contract package and remove the legacy/contract split — request/response models are split across at least four locations: `backend/api/contracts.py` (frontend-facing, ~37 models), `backend/api/routers/knowledgebases.py:54-91` (router-local `CreateKbRequest`, `DocumentRegistrationResponse`, `DocumentSummary`, `KbListResponse`, `DocumentListResponse`), `backend/api/routers/records.py:23-27` (`RecordPushRequest`), `backend/api/routers/ws.py:39-56` (WS subscribe filters), and service-layer `service_models.py` reused directly (`backend/api/routers/records.py:16` imports `RecordIngestReceipt`, `backend/api/routers/investigation.py:10-14` returns `graph.service_models.EntityDetailResponse`). The mix means contract evolution must touch multiple files, `openapi-typescript` (`chili_app/package.json:13`) consumes whatever name FastAPI emits, and there is no versioning boundary between `service_models` (internal) and `contracts` (external).
- **api.10** — Adopt a consistent paginated-collection contract and apply it to every list endpoint — `AlertListResponse` returns `items[] + PageInfo{page,page_size,total_items}` (`backend/api/contracts.py:43-47`), `KbListResponse` returns `items[] + total` (`backend/api/routers/knowledgebases.py:67-71`), `WorkflowRunListResponse` returns `items[]` only with no total (`backend/api/contracts.py:269-272`), `EntitySearchResponse` is `items + total=len(items)` after the search already capped at `limit` (`backend/api/routers/investigation.py:114-115` — `total` is wrong when results are paged), and `/policy/gaps` returns `items[] + PageInfo` but the underlying `ApiState.list_policy_gaps()` ignores limit/offset (`backend/api/routers/policy.py:31-35`). No cursor pagination, no `next_cursor`, no `Link: rel=next`. The acknowledge endpoint returns `ApiEnvelope{status: "accepted"|"ok", message}` (`backend/api/contracts.py:11-15`) and is the only generic envelope.
- **api.11** — Adopt a uniform filtering / sorting query convention — list endpoints accept ad-hoc query params: `/alerts` (`backend/api/routers/alerts.py:22-32`) takes none, `/workflows` accepts `knowledge_base_id`, `status`, `limit`, `offset` (`backend/api/routers/workflows.py:24-31`), `/knowledgebases` accepts only `limit`/`offset` (`backend/api/routers/knowledgebases.py:126-129`), `/investigation/search` uses `q`/`limit`/`offset` (`backend/api/routers/investigation.py:103-107`), and `/analytics/risk-scores` requires `kb_id` and accepts `entity_type` (`backend/api/routers/analytics.py:39-48`). No `?sort=`, no `?filter[severity]=`, no documented filter taxonomy, no shared `ListQueryParams` model.
- **api.12** — Tighten OpenAPI schema quality (operation IDs, `response_model` everywhere, error responses, tags) — `backend/api/app.py:116-120` sets only `title`/`version`/`description`; routes have no `operation_id` set, so `openapi-typescript` (`chili_app/package.json:13`) generates names like `register_knowledge_base_documents_knowledgebases__knowledge_base_id__documents_post`; `/config/*` endpoints return `dict[str, object]` with no `response_model` (`backend/api/routers/config.py:24-44`); `add_message` declares `response_model=None` because it forks between JSON and SSE (`backend/api/routers/rag.py:65-77`) and OpenAPI cannot describe either branch; `/events/stream` returns `StreamingResponse` and is invisible to the schema (`backend/api/routers/events.py:55-82`); no router declares the 401/403/404/409/413/415/422/500 response shapes, so generated clients have no typed error branches.
- **api.13** — Snapshot, publish, and lint the OpenAPI spec in CI — there is no checked-in `openapi.json` under `docs/` or `chili_app/`, no `make openapi-export` target, the only consumer is the manually-run `npm run codegen:api` (`chili_app/package.json:13`) which requires a running `http://localhost:8000/openapi.json`. No drift detection, no breaking-change checker (e.g. `oasdiff`), no `openapi-spec-validator`. Architecture §8.4 promises "the FastAPI backend auto-generates an OpenAPI specification" but the generated artifact is never persisted.
- **api.14** — Adopt a versioning strategy for the public API — every router today is mounted at the bare resource path (`/alerts`, `/knowledgebases`, `/chat`, `/events`, `/ws`, etc.; see `backend/api/app.py:142-156`); there is no `/v1` prefix, no `Accept-Version` header, no deprecation banner, no sunset metadata. The SPA in the same repo consumes the latest schema directly, so breaking changes today only need a frontend update — that pattern breaks the moment a published API contract supports an integration (Plugin SPI, BFF for partner tooling, customer scripts, future mobile app).
- **api.15** — Generate (and publish) a typed frontend API client from the OpenAPI spec — `chili_app/src/types/api.ts` is hand-maintained and `chili_app/src/lib/apiClient.ts` is hand-written; `chili_app/package.json:13` carries a `codegen:api` script that targets `http://localhost:8000/openapi.json` → `src/lib/api/schema.ts`, but `src/lib/api/` does not exist in the repo and `npm run codegen:api` is not run in CI. The hand-written client is allowed to drift from backend changes without any compile-time check.
- **api.16** — Stand up backend↔frontend contract tests — there is no Pact / consumer-driven contract test, no schemathesis run, no `openapi-spec-validator` step, and the frontend `.spec.ts` files under `chili_app/e2e/` (`smoke.spec.ts`, `alert-feed.spec.ts`, `knowledge-base-list.spec.ts`, etc.) drive the real UI against a live API but do not assert response-shape parity with the OpenAPI document. The closest existing coverage is `backend/tests/api/test_read_model_routers.py` which uses FastAPI's `TestClient` to assert shape against `api.contracts` Pydantic models for a happy path only.
- **api.17** — Move per-route policy declarations to a registry and audit on boot — every router today repeats `dependencies=[Depends(require_role("viewer"|"analyst"|"admin"))]` (40+ call sites across `backend/api/routers/*.py`); `backend/api/middleware/policy_registry.py:40-56 assert_complete` only checks each route has *some* `require_role` dependency by walking `route.dependant` for `_chiliai_required_role`, but cannot answer "list every admin-only endpoint", "what is the policy for `/workflows`", or "which routes changed policy between commits". The skip list (`SKIP_PREFIXES = ("/auth/", "/health", "/docs", "/openapi.json", "/redoc")` at `backend/api/middleware/policy_registry.py:12-18`) is hand-maintained. Move to a declarative registry that lists `(method, path, required_role, audit_event)` and have routes consume it; surface a `GET /policy/routes` for admin introspection.
- **api.18** — Add rate limiting and abuse-control headers to the API gateway — there is no rate-limit middleware anywhere under `backend/api/middleware/`; the only middleware registered in `backend/api/app.py:122-135` is CORS + metrics + tracing instrumentation. No per-IP, per-user, or per-tenant throttle on `/auth/login` (`backend/api/routers/auth.py:58-90` — vulnerable to credential brute-force via the IdP callback loop), no upload-bytes-per-minute cap (`/knowledgebases/{id}/documents` accepts files up to `validation.max_file_size_mb` * N files per call — `backend/api/routers/knowledgebases.py:401-422`), no per-user open-WebSocket cap (`backend/api/routers/ws.py:99-108`), and no chat-message-per-minute cap on `/chat/conversations/{id}/messages?stream=true` (`backend/api/routers/rag.py:65-105`) which holds an LLM call open for the duration of the request. Cross-edge to `_security.md` and `_infra.md` (a Redis-backed token-bucket likely lives at the gateway/middleware level).
- **api.19** — Split liveness, readiness, and dependency probes — `backend/api/app.py:137-139` defines a single `GET /health` that always returns `{"status": "ok"}` without checking event bus, graph repository, vector store, embeddings, object store, Postgres connection provider, or session store. There is no `/livez` vs. `/readyz` split, no per-dependency health surface, no warmup gate, no version/build-info endpoint, and no probe of `get_session_store()` Redis connectivity (`backend/api/dependencies.py:421-440`). K8s deployment manifests cannot distinguish "process is up" from "process is ready to serve traffic" and the `/health` route is also missing from the policy registry's skip-list audit reasoning (it works because the skip list at `backend/api/middleware/policy_registry.py:12-18` lists it).
- **api.20** — Add request-correlation IDs propagated through logs, traces, and downstream events — `backend/api/app.py:106 setup_tracing()` calls into `shared.tracing.instrument_fastapi_app(app)` for OTel HTTP spans, but there is no middleware that reads/generates `X-Request-Id` / `traceparent` and propagates it onto `EventBase.correlation_id` (`backend/events/types.py:14-20`) when a route publishes an event (e.g. `/knowledgebases` publishes `KnowledgeBaseCreatedEvent` at `backend/api/routers/knowledgebases.py:115-117`). The `chiliai_session` cookie carries no per-request id, so a 500 traced in the API cannot be cross-correlated to the worker side. Cross-edge to `_observability.md` and `events.md` epic 5 (W3C Trace Context).
- **api.21** — Plumb a per-request tenant context through middleware and into DI — there is no tenant axis anywhere in `backend/api/middleware/` or `backend/api/dependencies.py`; `User` (`backend/api/middleware/auth.py:52-58`) carries `user_id`, `roles`, `email` with no `tenant_id`. `get_api_state`, `get_knowledge_base_repository`, `get_alert_repository`, `get_workflow_run_store`, `get_graph_service`, `get_vector_store`, `get_session_store`, etc. (`backend/api/dependencies.py:162-808`) are process singletons keyed only by env/config, so even if a tenant claim were extracted from the JWT it has nowhere to flow. Hard cross-edge to `_multitenancy.md` (tenant binding source of truth) and `_security.md` (claim layout).
- **api.22** — Surface BFF auth-flow gaps (CSRF, login state, logout RP-initiated flow, refresh storms) — `backend/api/routers/auth.py:90 build_authorize_url(...)` writes PKCE state only after the URL builds (good) but the cookie at `backend/api/routers/auth.py:163-172` is `SameSite=lax` with no double-submit-token / `_csrf` for state-changing endpoints; `/auth/logout` accepts a `post_logout_redirect_uri` query param with no allow-list (`backend/api/routers/auth.py:181-204` — open-redirect surface against the IdP `end_session_endpoint`); session refresh in `_maybe_refresh_session` (`backend/api/middleware/auth.py:251-298`) is per-request, not coalesced, so N concurrent requests near expiry will issue N refreshes; `JwksCache._clock=time.monotonic` (`backend/api/middleware/auth.py:89`) means the JWKS TTL is process-uptime-based, not wall-clock, which can hide rotation issues across restarts.
- **api.23** — Harden the session store production surface — `RedisSessionStore.__init__` (`backend/api/middleware/session_store.py:87-108`) uses `decode_responses=True` and exposes no connect/socket timeout, no pool sizing, no TLS toggle, no health-check, no key prefix audit, and no session-revocation event. `InMemorySessionStore` (`backend/api/middleware/session_store.py:54-84`) carries a `# Thread-naive` warning in its docstring and is the default any time `AuthConfig.enabled=False` regardless of `CHILI_ENV` (`backend/api/dependencies.py:421-440`). Cross-edge to `_security.md` and `_infra.md`.
- **api.24** — Open the closed `WorkflowRunResponse.workflow_type` enum — `backend/api/contracts.py:260-261` declares `workflow_type: Literal["ingestion", "graph_build", "analytics", "monitoring"]` and `backend/api/_workflow_projection.py:87-97 _workflow_type_for_trigger` maps every event prefix to one of those four; a new event family (e.g. `records.*`) is silently bucketed into `"ingestion"`. The closed `Literal` blocks adding workflow types without a coordinated frontend/contract change.
- **api.25** — Add admin write surface for runtime config and ops actions — `backend/api/routers/config.py:18-21` carries a `TODO(production)` for `POST /config/domain` (update with validation), `POST /config/reload` (force reload), ETag / Last-Modified headers, and change-audit logging; `backend/api/routers/workflows.py:19-39` only mounts `GET /workflows` even though `AgentServiceProtocol` exposes `submit_workflow`, `cancel_workflow`, and DLQ listing (cross-referenced from agent.md Epic 19). There is no admin-only ops surface for DLQ replay, alert backfill, JWKS cache invalidation, session revoke, or hot reload.
- **api.26** — Fix DI mis-wirings in `dependencies.py` flagged by the code today — `get_chat_message_payload` (`backend/api/dependencies.py:248-256`) calls `get_knowledge_base_repository()` directly without `Depends`, bypassing FastAPI's override mechanism and making tests unable to inject a fake KB repo for that path; `get_object_store()` returns `InMemoryObjectStore` only when `storage` section is at default (`backend/api/dependencies.py:447-453`) which silently switches storage backends if any non-default value is set; `get_session_store` is `@lru_cache(maxsize=1)` (`backend/api/dependencies.py:421-422`) but reads `os.environ["REDIS_URL"]` at first call — env mutations after the first call are ignored even by tests, and the cache is never cleared by `create_app()` (only `get_domain_config` is at `backend/api/app.py:110-111`).
- **api.27** — Document the route surface (machine-readable + curated guide) — no `docs/api/` directory exists, the only API documentation is the auto-generated `/docs` (Swagger UI from FastAPI), and `docs/architecture.md` §8.4 references the OpenAPI spec but does not enumerate routes; the README.md files under `backend/` do not list endpoints. Need (a) an exported, version-controlled `openapi.json` (Epic 13), (b) a curated `docs/api/README.md` that lists every public route with its required role, request/response contract, error envelope, pagination and idempotency notes, and (c) a "deprecated routes" page once Epic 14's versioning lands.

### Open questions
- How much of `ApiState` (`backend/api/state.py`) is a true fallback that should disappear (Epic 1) versus a deliberate "demo seed" that should move to a `tools/seed_demo_state.py` script with the same data? Affects sequencing of Epics 1–4 and whether a feature flag (`CHILI_DEMO_SEED=true`) survives the rewrite.
- Are cases, conversations, and policy gaps in scope for the api/ module's persistence epics (2, 3, 4) or should they move to their own modules (e.g., `cases/`, `chats/`, `policy/`) under `backend/`? Affects file ownership and the boundary rules in §5.2.
- For the WS Redis bridge (Epic 5), do we keep one bridge per API process (each subscribes to the same consumer group with `XREADGROUP` and fans out to local clients) or run a dedicated bridge worker that publishes to API instances over a pub/sub channel? Architecture §4 mentions Redis pub/sub as a possibility but is non-committal.
- For SSE (Epic 7), do we keep `text/event-stream` as the primary transport or replace it with Server-Sent WebSockets / fetch-streams from the SPA? Affects reconnect semantics and the polyfill story.
- Error envelope (Epic 8): RFC 7807 `application/problem+json` (standard, but JSON-shape change for every client) vs. extend the existing `ApiEnvelope` model (`backend/api/contracts.py:11-15`) with `error_code` + `details` (less invasive but non-standard). Affects every router and the frontend apiClient.
- Pagination (Epic 10): cursor-based (`?cursor=...`) with opaque tokens, or stay with `?limit`/`?offset` and add a uniform `PageInfo` everywhere? Cursor is more robust at scale but rules out random-access UI; offset is what most existing routers already accept.
- Versioning (Epic 14): URL-prefixed `/v1/...` (cache-friendly, breaks every existing URL when v2 ships) vs. header `Accept-Version: 2` (cleaner URLs, harder for CDNs and gRPC bridges). Affects every router mount line in `backend/api/app.py:142-156`.
- Contract package (Epic 9): `backend/api/contracts/` (per-router submodules) vs. `backend/shared/contracts/` (importable by the SPA codegen consumer directly via OpenAPI). Affects whether `service_models.py` becomes purely internal.
- Tenant binding (Epic 21): tenant claim resolved from JWT vs. `X-Chili-Tenant` header vs. subdomain (`tenant-acme.chiliai.example.com`). Resolution affects `_multitenancy.md` Epic 1 and the BFF cookie domain (`backend/api/routers/auth.py:170` `domain=auth_config.cookie_domain`).
- Admin ops surface (Epic 25): does this become a separate `/admin/...` router family with its own RBAC tier ("super-admin") or stay folded into existing routers with `require_role("admin")`? Affects audit scope and the policy registry shape (Epic 17).
- For the route-policy registry (Epic 17), should the registry double as the auth source of truth (route → role) and remove the per-route `dependencies=[Depends(require_role(...))]` decorators, or sit alongside as a verification-only artifact? Removing the decorators makes the audit single-sourced but requires a new middleware to enforce policy from the registry on every request.

### Open questions
- Should `stream_generate` be `async` (current `LlmServiceProtocol.generate_stream` signature) or sync iterator (current `LlmClientProtocol` would need a parallel sync method, mirroring `RagAnswerGenerator.stream_generate`)? The rag bridge and SSE writer are sync today; flipping to async would propagate up through `RagService.stream_answer` and `api/routers/rag.py:_stream_sse`.
- Should JSON-mode be a `GenerationRequest.response_format` field (caller picks per-call) or a `LlmConfig.json_mode` toggle (config-time per-deployment)? The ingestion extractor wants per-call; future tool-use plus JSON-mode combinations argue for per-call.
- Should the prompt template registry live in `backend/llm/prompts/` as a filesystem-backed registry (versioned in git, simple) or in Postgres via `database.ConnectionProvider` (mutable at runtime, auditable, but adds a migration)? The §14.2 audit-log requirement leans Postgres; the prototype velocity leans filesystem.
- Should the response cache be keyed on the full message list (safe, never collides) or on a normalized `(model, system_prompt, user_prompt, temperature)` tuple (higher hit rate, may collide if hidden state matters)? The embeddings module faces the same question — pick once and share.
- Should the model-capability registry be hard-coded in `backend/llm/capabilities.py` (matches embeddings' dimension-table option), discovered at adapter construction via a `health_check()` probe, or pulled from each provider's `/v1/models` endpoint? Hard-coded drifts; probed costs a startup round-trip and assumes the provider exposes capabilities.
- Should the multi-model router be a request-time `model_name` switch (caller picks, similar to `GenerateRequest.model_name` today) or a `task_class` enum (caller declares intent, router picks the model from a policy table)? The latter decouples callers from provider model identifiers but introduces a policy-config surface.
- Does the circuit-breaker open per-`(provider, model)` or per-`provider` regardless of model? OpenAI 5xx on `gpt-4o` does not necessarily imply `gpt-4o-mini` is unhealthy; per-`(provider, model)` is finer-grained but multiplies state.
- Should prompt-injection defense reject suspicious content (hard fail with a `LlmConfigurationError`) or sanitize and continue (silent strip with a metric counter)? ### Open questions
- Should the live wiring (epic 1) flip `ApiState`'s singleton over wholesale, or should we keep a `CHILI_RAG_PROFILE=seeded|live` toggle so demos and tests still get the deterministic canned answers? The seeded `_build_context_records` (`backend/api/state.py:830-846`) is also the only data that makes the chat page non-empty without an end-to-end ingestion+embed pipeline.
- For multi-KB fan-out (epic 2), do we (a) call retrieval once with the full `knowledge_base_ids` list (current `VectorSearchRequest` shape), (b) call once per KB and fuse with RRF / weighted-merge, or (c) treat the reference (policy) KB as a second-pass enrichment after the primary retrieves? Each has different implications for `top_k` semantics, score comparability across KBs, and per-KB attribution on citations.
- For citation extraction (epic 4), do we ask the LLM to emit numeric markers (`[1]`, `[2]`) that we parse out (cheap, brittle), use JSON-mode / structured-output to return `{answer, citations[]}` (cleaner, more provider-specific), or run a second judge LLM pass that maps the answer to the retrieved set (most accurate, doubles cost)?
- For conversation history (epic 5), do we summarize older turns into a rolling memory once the window fills, drop oldest first, or carry the raw transcript and let epic 12's budget squeezer truncate? Each affects the believability of long investigations.
- For the reranker (epic 7), does `RagConfig.reranking_enabled` carry a `reranker_backend` field (literal: `none | cross_encoder | llm_judge`) so domains can pick, or do we ship a single default and add config later? The latter is simpler but locks in cost/latency choices.
- For hybrid retrieval (epic 8), do we expose `RagQueryRequest.retrieval_mode` to callers (analyst can toggle vector-only vs hybrid for a single question) or treat it as a domain-config-only knob? The former is great for debugging, terrible for prompt caching.
- For evals (epic 10), do gold question sets live in the repo under `backend/tests/fixtures/rag_gold/` (versioned, public) or in object storage referenced by domain config (private per deployment)? Medicare fraud gold sets may contain sensitive language.
- For prompt caching (epic 16), do we adopt the OpenAI / Anthropic native prompt-cache headers (provider-specific, no chiliAI code beyond the marker), build our own KV cache keyed by prompt hash (provider-agnostic, second cost), or both layered? The architecture endgame implies "both" but ordering matters for epic 1 sequencing.
- For tenant scoping (epic 17), does the RAG service become per-tenant (one `RagService` instance per tenant with bespoke wiring/quotas) or stay singleton with tenant as a request parameter? Per-tenant is cleaner for quota+cache isolation but multiplies process memory.
- The four `Service*` bridges live in `backend/api/_rag_bridges.py` to keep `rag/` free of sibling-module imports per architecture §5.3. Do they stay there forever, or do they move into `rag/adapters/` once we accept that the protocol+adapter rule was meant for external systems (DB, LLM) rather than sibling services, and the indirection costs us discoverability? Affects where new bridges (reranker, hybrid retriever, citation extractor) live.

### Notes from auditor (edges, open questions)

### Open questions

1. Epic 2 / Epic 3 — should pgvector and Weaviate ship together (one "extra adapters" epic) or sequenced (pgvector first because Postgres is already in the stack via `database/`)? Sequencing matters for the shared contract test suite's design.
2. Epic 4 (snapshot tooling) — does the in-memory adapter need snapshot support at all, or is a stub `NotImplementedError` acceptable since in-memory is dev/test only? Test fixtures may want JSON round-trip for replay debugging.
3. Epic 5 (namespace reshape) — blue/green vs in-place. Blue/green doubles peak storage during migration; in-place blocks writes. The right choice depends on whether the platform tolerates write downtime during reshape — needs an SLO decision.
4. Epic 6 (sharding) — what's the prod load target the benchmark should be sized for? Architecture §6 (cycle KBs) implies per-cycle KBs are bounded but the reference policy KB may be millions of vectors. Pick a representative working-set size.
5. Epic 7 (rich filters) — should the new filter model be exposed at the public API as a structured DSL or kept service-internal with the API translating from a flatter query shape? Influences API stability.
6. Epic 9 — should the event for source-doc delete be a new `VectorsDocumentDeletedEvent` or reuse `VectorsDeletedEvent` with an optional `source_document_id`? Schema evolution implications for monitoring consumers.
7. Epic 10 (tenant scoping) — defer to `_multitenancy.md` for the cross-cutting decision (collection-prefix vs per-cluster vs native multi-tenancy) and inherit it here, or make the decision here because Qdrant collection naming is module-local?
8. Epic 13 (recall@k) — is a ground-truth eval set within scope of this module (vectorstore owns the harness) or does it belong to `rag.md` (RAG owns retrieval quality, vectorstore only exposes hooks)?
