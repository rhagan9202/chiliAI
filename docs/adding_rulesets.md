# Adding Policy Intelligence Rule Sets

> Developer guide for the Policy Intelligence rule-pack surface (BL-011).
> See also: [`backend/policy/README.md`](../backend/policy/README.md), the design spec
> [`docs/superpowers/specs/2026-06-04-policy-intelligence-v1-design.md`](superpowers/specs/2026-06-04-policy-intelligence-v1-design.md),
> and the config schema reference [`docs/ledger/config-schema.md`](ledger/config-schema.md).

Policy Intelligence items are **not hand-seeded** — in production they are generated by the
worker from **domain-configured rule packs**. This guide explains how that works and how to
author your own rules.

## The short version

There are **two completely different ways** a Policy Intelligence item can appear, and they
have different requirements:

| Path | How items are created | Depends on `config.policy_rules`? |
|------|----------------------|-----------------------------------|
| **A. Worker (the real/production path)** | The worker watches ingested data and auto-generates items when a configured rule matches | **Yes** — if the active config has no rules, it generates **nothing** |
| **B. Dev-seed (test-only shortcut)** | The `/admin/dev-seed` endpoint inserts one item *directly* into the repository | **No** — it bypasses the worker and config entirely |

The most common "the Policy page is empty" confusion is that **the active config file ships no
rules**, so the *worker* path produces nothing out of the box — even though the feature is fully
working (the e2e is green because it uses path B).

## The concrete facts

**1. The dev stack loads a specific config** via `CHILI_CONFIG_PATH` (`docker-compose.dev.yaml`,
for both the API and the worker):
```
CHILI_CONFIG_PATH=/app/config/defaults/medicare_fraud_cms_desynpuf.yaml
```

**2. Each default config independently chooses whether to ship a `policy_rules:` block:**
```
HAS policy_rules:  medicare_fraud.yaml                 ← threshold max_billed_amount: 5000
HAS policy_rules:  medicare_fraud_cms_desynpuf.yaml    ← THIS is what the stack uses (added for the demo)
no  policy_rules:  food_supply_chain.yaml
```
`medicare_fraud_dev.yaml` also carries a `policy_rules` block (threshold
`max_billed_amount: 100`), but it now lives at `backend/config/overlays/` as
a **partial overlay** over `medicare_fraud.yaml` (ADR 0001,
`CHILI_CONFIG_OVERLAY_PATH`) rather than a standalone config — see Example B
below.

**3. The worker only evaluates rules from the loaded config.** In `backend/agent/coordinator.py`:
```python
# build_worker_dependencies():
policy_rules = list(config.policy_rules)          # → [] when the config ships no rules

# handle_records_ingested():
if policy_service is not None and policy_rules:    # ← [] is falsy, so this is SKIPPED
    _evaluate_policy_rules(...)
```
So with a rule-less config, `policy_rules == []`, the `if` is skipped, and **no matter how many
claims you ingest, the worker creates zero policy items.**

**4. The dev-seed endpoint bypasses all of that.** In `backend/api/routers/dev_seed.py` it calls
the service directly:
```python
policy_service.record_match(rule_id="claim_over_billed", target_ref=claim_id, ...)
```
That is why the e2e (`policy-triage.spec.ts`) works — it never relies on the worker or the config
rules.

## Concrete examples

### Example A — a config that ships **no** rules
1. The stack loads a config whose `policy_rules` is absent/empty (e.g. `food_supply_chain.yaml`).
2. You upload a CSV of 1,000 claims, some with `amount = $50,000`.
3. The worker ingests them, builds the graph… and evaluates **zero** rules.
4. You open the **Policy Intelligence** page → **empty queue**.
5. ➡️ This looks like "the feature doesn't work," but it's actually "this config defines no policy
   rules." Nothing is broken.

### Example B — making live (worker-generated) items appear
Point the stack at a config that ships rules. For instance, layering the dev
overlay onto the base pack (`CHILI_CONFIG_PATH=config/defaults/medicare_fraud.yaml
CHILI_CONFIG_OVERLAY_PATH=config/overlays/medicare_fraud_dev.yaml`) merges in
this `policy_rules` block:
```yaml
policy_rules:
  - id: billing_thresholds
    thresholds:
      max_billed_amount: 100            # low, so it trips easily in dev
    rules:
      - id: claim_over_billed
        title_template: "Claim {target_ref} exceeds the billing threshold"
        severity: high
        target_kind: entity
        target_selector: { entity_type: claim }
        predicate:
          field: properties.amount       # the claim entity's amount property
          op: gt
          value: { config_ref: max_billed_amount }
```
Now:
1. `make dev` → worker has 1 rule.
2. You ingest a claim with `amount = 1500` (> 100).
3. The worker maps it to a `claim` entity, evaluates the rule, `1500 > 100` is true → it calls
   `record_match` → **a durable policy item is created.**
4. Policy Intelligence page → shows **"Claim claim-XXX exceeds the billing threshold"**, which you
   can triage/escalate. No dev-seed involved.

### Example C — making a particular config generate items
Add a `policy_rules:` block to the config the stack actually loads (same shape as above), tuned to
that dataset's field names/thresholds. Then the stack's default config generates live items without
changing `CHILI_CONFIG_PATH`. **This is exactly what we did for `medicare_fraud_cms_desynpuf.yaml`
— see the [worked example](#worked-example-shipped-in-medicare_fraud_cms_desynpufyaml) below.**

## Why it's this way (not a defect)

- `policy_rules` is intentionally **additive/optional** (default `[]`) so that configs *without* it
  still load — a deliberate design decision (it's what lets `food_supply_chain.yaml` work unchanged).
- The gap is **config coverage, not code.** The engine works; a config that ships no rules simply
  feeds it nothing.

## How to author a rule pack

Rules live entirely in the domain config (`DomainConfig.policy_rules`) — no code change is needed
to add, tune, or remove them. The shape (defined in `backend/config/schema.py`):

```yaml
policy_rules:                 # list[PolicyRulePack]
  - id: <pack-id>             # unique pack id
    name: "<human name>"
    description: "<optional>"
    thresholds:               # named values a predicate can reference by config_ref
      <key>: <number|string|bool>
    rules:                    # list[PolicyRule]
      - id: <rule-id>
        title_template: "<text with {target_ref} placeholder>"
        severity: medium | high | critical
        target_kind: entity | metric | alert
        target_selector:      # which targets the rule applies to
          entity_type: <type>     #   for target_kind: entity
          # metric_name: <name>   #   for target_kind: metric
        predicate:            # exactly ONE comparison (v1: one predicate per rule)
          field: "<field>"    # see "Predicate fields" below
          op: eq | neq | gt | gte | lt | lte | in | not_in
          value:              # exactly one of literal / config_ref
            literal: <scalar or list[str]>
            # config_ref: <thresholds key>
        citations:            # optional; surfaced on every generated item
          - citation_id: <id>
            title: "<title>"
            source_ref: "<ref/url>"
            excerpt: "<optional>"
```

### Target kinds
- **`entity`** — evaluated against each entity of `target_selector.entity_type`. `target_ref` is the
  entity id. Supported fields: `properties.<name>` and `risk_score`.
- **`metric`** — evaluated against a KB-level graph metric named by `target_selector.metric_name`.
  `target_ref` is the metric name. Supported fields: `metric.<name>` (the worker currently supplies
  `entity_count`, `relationship_count`, `avg_degree`).
- **`alert`** — *defined but not yet evaluated in v1* (documented non-goal). Alert-target rules load
  fine but generate no items yet.

### Operators
`eq`, `neq`, `gt`, `gte`, `lt`, `lte` (numeric comparisons coerce both sides to a number), and
`in` / `not_in` (membership against a `literal` list, e.g. `value: { literal: ["FL", "TX"] }`).

### `literal` vs `config_ref`
A predicate value must set **exactly one** of:
- `literal:` — an inline value (`1500`, `"TN"`, `["FL", "TX"]`), or
- `config_ref:` — the name of a key in the owning pack's `thresholds:` map.

`config_ref` keys are **validated at config-load time**: a ref pointing at a threshold the pack does
not declare raises a `ValueError` at startup (see `PolicyRulePack._validate_config_refs` in
`backend/config/schema.py`), so a typo fails fast rather than silently producing an empty queue.

### Lifecycle notes
- Items are upserted by the natural key `(knowledge_base_id, rule_id, target_ref)`; re-evaluation
  refreshes an open item in place and **never reopens** an already-triaged item.
- Evaluation is **best-effort** in the worker — a rule error is logged and never aborts ingestion.
- Metric-target evaluation is throttled per KB (its own throttle, independent of the graph-metrics
  flow), so a burst of ingests does not thrash `compute_metrics`.

### Apply your changes
Rule packs are plain config — `make dev` (or a worker restart) picks them up; there is **no codegen
or migration**. To validate before you run the stack:
```bash
cd backend
.venv/bin/python -c "from config.loader import load_config; \
  print([p.id for p in load_config('config/defaults/<your>.yaml').policy_rules])"
.venv/bin/pytest -q tests/config/test_loader.py tests/config/test_policy_rules_demo.py
```

## Worked example (shipped in `medicare_fraud_cms_desynpuf.yaml`)

The config the dev stack loads ships four demo-tuned packs so that a plain `make dev` + ingest of the
TN DE-SynPUF subset produces live items. All three target-kinds are demonstrated (`entity` via
claim/provider properties, `metric` via KB size), and the thresholds are deliberately low for the
demo (raise them for real screening). The first two packs are shown in full below; two more
provider-targeted packs (`outlier_billing_concentration`, `referral_ring_exposure`) follow the same
shape and cover the demo's UPCODING and referral-ring patterns — see the YAML file for their full
definitions.

```yaml
policy_rules:
  # Entity-target rule on the claim payment amount.
  - id: elevated_payment_claims
    name: "Elevated payment claims"
    description: "Claims whose Medicare payment exceeds the analyst-review threshold."
    thresholds:
      min_elevated_amount: 500
    rules:
      - id: claim_elevated_payment
        title_template: "Claim {target_ref} payment exceeds the elevated-review threshold"
        severity: high
        target_kind: entity
        target_selector: { entity_type: claim }
        predicate:
          field: properties.amount          # mapped from LINE_NCH_PMT_AMT_1 / CLM_PMT_AMT / TOT_RX_CST_AMT
          op: gt
          value: { config_ref: min_elevated_amount }
        citations:
          - citation_id: cms-pim-ch3
            title: "CMS Program Integrity Manual, Ch. 3 — claims review"
            source_ref: "policy://cms/pim/chapter-3"
            excerpt: "High-dollar claims are prioritized for medical-review screening."

  # Metric-target rule on KB size.
  - id: graph_scale_watch
    name: "Graph growth watch"
    thresholds:
      max_entities: 50
    rules:
      - id: kb_entity_volume
        title_template: "Knowledge base {target_ref} crossed the entity-volume watch line"
        severity: medium
        target_kind: metric
        target_selector: { metric_name: entity_count }
        predicate:
          field: metric.entity_count
          op: gt
          value: { config_ref: max_entities }
```

**What trips them**
- `claim_elevated_payment` fires for every ingested `claim` entity whose `amount` exceeds **$500**
  (inpatient/outpatient/PDE claims routinely clear this; small carrier line items stay below).
- `kb_entity_volume` fires once a KB accumulates more than **50** entities — which the TN subset
  ingest easily exceeds — surfacing one medium item per KB.
- `provider_outlier_billing` (pack `outlier_billing_concentration`) fires for `provider` entities
  whose `risk_score` (written by the peer-deviation/self-history anomaly signals) is **>= 0.35** —
  live TN passes showed provider composites in the ~0.33-0.42 range, so this catches the top
  providers; severity `high`.
- `provider_repeat_flag_exposure` (pack `referral_ring_exposure`) fires for `provider` entities
  whose `properties.active_alert_count` (snapshotted by Flow 4 from open alerts) is **>= 2** —
  a proxy for the demo's referral-ring pattern; severity `critical`.

**Try it**
1. `make dev`
2. Ingest the TN DE-SynPUF subset (carrier/inpatient/outpatient claims + NPPES providers).
3. Open **Policy Intelligence** → see high-value-claim items (high), a graph-volume item (medium),
   outlier-billing-concentration items (high), and referral-ring-exposure items (critical after a
   provider accumulates repeat alerts across detection runs) — each triageable; **Escalate** promotes
   one into a Case.

The regression test `backend/tests/config/test_policy_rules_demo.py` loads this config and asserts
all four packs' rules fire on representative data, so a future config edit can't silently break the
demo.
