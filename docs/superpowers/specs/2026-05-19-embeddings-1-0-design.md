# Embeddings 1.0 Design

## Summary

Embeddings 1.0 hardens `backend/embeddings` into a release-ready, synchronous embedding subsystem with production text providers and a forward-compatible graph embedding channel.

The release keeps semantic text embeddings and graph/node embeddings separately indexable. Text embeddings remain the default path for RAG, semantic search, and citations. Graph embeddings are added as a separate channel for clustering, graph similarity, and graph-learning workflows. The embeddings module owns the multi-channel result contract, but it does not import analytics, graph, vectorstore, API, or agent internals.

## Goals

- Keep the embeddings API synchronous for 1.0.
- Preserve existing text embedding behavior for OpenAI, sentence-transformers, and in-memory providers.
- Add a graph embedding channel sourced through an embeddings-owned protocol, not by importing `analytics.gnn`.
- Persist text and graph vectors as separate channels in embedding artifacts.
- Index text and graph vectors as separate vectorstore records with explicit channel metadata.
- Keep RAG query embeddings and retrieval text-only by default.
- Add architecture tests that enforce module and SDK boundaries.
- Add live smoke coverage for provider integrations where credentials/dependencies are available.

## Non-Goals

- No async embeddings API.
- No new public HTTP endpoint expansion unless required by existing dependency wiring.
- No learned GNN training changes.
- No blended ranking or combined text+graph retrieval algorithm.
- No graph-channel retrieval in RAG by default.
- No cross-module imports from `embeddings` into `analytics`, `graph`, `vectorstore`, `api`, or `agent`.

## Current State

The existing module has:

- `EmbeddingsService.embed(EmbedRequest) -> EmbedResponse`.
- `EmbedderProtocol.embed(EmbeddingRequest) -> EmbeddingResult`.
- In-memory, OpenAI, and sentence-transformers adapters.
- Config-driven adapter selection in API and agent composition roots.
- Agent workflow support that embeds graph-updated entities, persists an `EmbeddingResult`, emits `embeddings.complete`, and indexes vectors afterward.
- RAG query embedding through `ServiceQueryEmbedder`, which depends on `EmbeddingsServiceProtocol`.

The current result shape is effectively single-channel: `EmbeddingResult.vectors` maps `content_id` to one vector. That is too narrow for graph embeddings because text and graph vectors serve different retrieval and analytics purposes and may have different dimensions.

## Architecture

Embeddings 1.0 uses a multi-channel result model.

The embeddings module owns:

- text embedding request and response models;
- multi-channel artifact models;
- provider adapter protocols;
- graph embedding provider protocol;
- service-level orchestration that combines optional channels without coupling to analytics implementations.

The composition layer owns:

- constructing concrete text embedders;
- adapting `GnnServiceProtocol` to the embeddings-local graph provider protocol;
- wiring optional graph embedding support into `EmbeddingsService`;
- passing the resulting multi-channel artifact to downstream vector indexing.

The vectorstore module remains responsible for storing/searching vectors. It should receive separate records per channel, with channel metadata and stable record IDs. It must not learn about GNN internals.

## Channel Model

1.0 supports two channels:

- `text`: semantic text embedding generated by the configured embedder.
- `graph`: node embedding returned by a graph embedding provider.

Each vector item should carry:

- `content_id`
- `channel`
- `vector`
- `dimensions`
- `model_name`
- `provider`
- `created_at`

The request should support:

- `include_graph_embeddings: bool = False`
- `require_graph_embeddings: bool = False`
- `graph_embedding_dimension: int = 8`

`include_graph_embeddings` requests the graph channel. `require_graph_embeddings` changes graph failures from non-blocking to blocking. `graph_embedding_dimension` is passed to the graph provider and validates returned graph vector sizes.

## Graph Provider Boundary

`backend/embeddings` defines a narrow protocol:

```python
class GraphEmbeddingProviderProtocol(Protocol):
    def get_node_embeddings(
        self,
        *,
        knowledge_base_id: str,
        content_ids: Sequence[str],
        dimensions: int,
    ) -> GraphEmbeddingBatch: ...
```

`GraphEmbeddingBatch` is an embeddings-owned model containing:

- `vectors: dict[str, list[float]]`
- `model_name: str`
- `provider: str`
- `dimensions: int`

The contract is:

- call by knowledge base and requested content IDs;
- return vectors keyed by content ID;
- expose provider/model metadata;
- never expose analytics/GNN concrete types to `embeddings`.

The agent or API composition root may implement an adapter that calls `GnnServiceProtocol.analyze(GnnAnalysisRequest(...))` and maps `GnnAnalysisResponse.node_embeddings` into this embeddings-local shape. That adapter may live outside `backend/embeddings` because composition roots are allowed to wire sibling modules.

## Embeddings Service Flow

`EmbeddingsService.embed()` should:

1. Normalize the public `EmbedRequest` into an internal `EmbeddingRequest`.
2. Always call the configured text `EmbedderProtocol`.
3. Validate that text vectors cover exactly the requested content IDs.
4. Build text-channel response items in submission order.
5. If `include_graph_embeddings` is false, return only text vectors.
6. If graph embeddings are requested and no graph provider is configured:
   - omit graph vectors when `require_graph_embeddings` is false;
   - raise `EmbeddingProviderError` when `require_graph_embeddings` is true.
7. If graph embeddings are requested and a graph provider is configured:
   - request graph vectors for the same content IDs;
   - validate returned vector dimensions;
   - add graph-channel vectors for IDs that returned valid graph vectors.
8. Omit missing graph vectors by default and record missing IDs in the response/artifact.
9. Raise when graph vectors are missing or malformed if `require_graph_embeddings` is true.
10. Publish `embeddings.generated` only after at least text vectors are valid.

Missing graph vectors should not be zero-filled. Omitting them keeps downstream consumers from treating absent graph signal as real graph geometry.

## Artifact Persistence And Workflow

The existing agent workflow persists an `EmbeddingResult` artifact after graph updates. In 1.0 that artifact should become multi-channel while preserving enough compatibility for existing tests and consumers.

The artifact should include:

- request ID;
- knowledge base ID when available;
- text model/provider metadata;
- per-vector channel metadata;
- vectors grouped or listable by content ID and channel;
- graph channel status:
  - requested;
  - provider configured;
  - missing content IDs;
  - failure message when non-blocking graph embedding failed.

Coordinator behavior:

- Entity text generation remains in the agent workflow.
- The coordinator passes `include_graph_embeddings=True` for the full workflow when GNN capability is enabled and a graph provider adapter is available.
- The coordinator persists the multi-channel result artifact.
- The coordinator publishes `embeddings.complete` with the artifact key as today.

## Vector Indexing

`handle_embeddings_complete` should index each vector channel as a distinct vectorstore record.

Record identity should be stable and channel-specific:

- text: `{knowledge_base_id}:{content_id}:text`
- graph: `{knowledge_base_id}:{content_id}:graph`

Metadata should include:

- `embedding_channel`: `text` or `graph`
- `embedding_model_name`
- `embedding_provider`
- `embedding_dimensions`
- existing provenance metadata such as knowledge base, entity ID, source document ID, extraction result ID, and validation report ID

This keeps text vectors separately searchable from graph vectors. RAG and citation flows should filter retrieval to `embedding_channel=text`.

Graph vectors may have a different dimension from text vectors. Because most vector stores enforce one dimension per collection/namespace, 1.0 uses channel-specific vectorstore namespaces:

- text vectors use the existing knowledge-base namespace: `{knowledge_base_id}`;
- graph vectors use a graph-channel namespace: `{knowledge_base_id}__graph`;
- record metadata always preserves the original `knowledge_base_id` and `embedding_channel`.

This keeps current text/RAG behavior stable while allowing graph vectors to have their own collection dimension. It must not mix text and graph vectors with different dimensions in one Qdrant collection.

## RAG Behavior

RAG query embedding remains text-only.

`ServiceQueryEmbedder` should continue to call `EmbeddingsServiceProtocol.embed()` for one text query and return the text vector. Retrieval should filter to `embedding_channel=text` so graph records do not pollute citation-bearing semantic search.

No graph-channel query embedding or blended retrieval is part of 1.0.

## Error Handling

Text provider failures are blocking:

- configuration errors raise `EmbeddingConfigurationError`;
- provider call failures raise `EmbeddingProviderError`;
- incomplete text batches raise `EmbeddingProviderError`;
- no `embeddings.generated` event is published after text failure.

Graph provider failures are non-blocking by default:

- missing provider, missing vectors, provider exceptions, or dimension mismatches omit graph vectors and record status in the artifact;
- text vectors still return and are indexable;
- event publication still occurs when text vectors are valid.

Graph provider failures become blocking when `require_graph_embeddings=True`:

- missing provider raises `EmbeddingProviderError`;
- missing requested IDs raise `EmbeddingProviderError`;
- malformed dimensions raise `EmbeddingProviderError`;
- provider exceptions raise `EmbeddingProviderError`.

Provider SDK exceptions stay behind their adapters and are normalized to embeddings exceptions.

## Architecture Guardrails

Add tests that enforce:

- `backend/embeddings` does not import `analytics`, `graph`, `vectorstore`, `api`, or `agent`.
- `openai` SDK imports stay in `embeddings/adapters/openai_adapter.py` and OpenAI tests.
- `sentence_transformers` imports stay in `embeddings/adapters/sentence_transformers_adapter.py` and sentence-transformers tests.
- The graph embedding bridge lives in a composition boundary, not inside `backend/embeddings`.

## Testing Strategy

Unit tests should cover:

- service models for multi-channel vectors and request flags;
- text-only embeddings remain backward-compatible;
- graph channel success with a fake graph provider;
- missing graph vectors are omitted and reported;
- required graph vectors raise;
- graph dimension mismatch is non-blocking by default and blocking when required;
- OpenAI adapter batching, retries, shape validation, and optional live smoke;
- sentence-transformers batching, normalization, shape validation, and optional local smoke;
- in-memory deterministic behavior;
- coordinator artifact persistence with text and graph channels;
- vector indexing creates channel-specific record IDs and metadata;
- RAG query embedding remains text-only.

Release gates:

- `uv run --project backend pytest backend/tests/embeddings backend/tests/rag/test_embeddings_bridge.py -v`
- targeted coordinator/vector indexing tests touched by the implementation;
- `uv run --project backend pytest --cov=embeddings --cov-report=term-missing backend/tests/embeddings` with at least 90% coverage;
- targeted `ruff check`;
- targeted `pyright`;
- live OpenAI smoke when `OPENAI_API_KEY` is present;
- optional sentence-transformers smoke when the dependency and model are locally available.

## Release Readiness Criteria

Embeddings 1.0 is ready when:

- text embedding behavior is preserved;
- graph embeddings can be produced through the protocol bridge without importing analytics inside embeddings;
- persisted embedding artifacts represent text and graph vectors separately;
- vector indexing safely separates graph/text namespaces;
- RAG retrieval remains text-only;
- architecture guards pass;
- live/provider tests are documented and gated by environment availability;
- docs describe supported providers, graph channel behavior, failure semantics, and non-goals.
