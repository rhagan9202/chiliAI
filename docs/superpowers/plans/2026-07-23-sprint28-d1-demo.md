# Sprint 2026-28 D1 — Scripted CMS Demo Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** BL-051: a presenter script at `docs/demo/` walking every capability on the 1% TN subset, `make demo-cms` orchestration (stack-up + data staging + ingest + readiness probes), 2–3 demo-tuned CMS fraud rule packs in the existing policy-rule schema (configured, not coded), and a full-stack e2e spec that mechanically validates the walkthrough so the demo cannot silently rot. Sprint DoD: the walkthrough runs green end-to-end on a fresh `make dev` + `make demo-cms`.

**Architecture:** Everything composes existing machinery: rule packs extend `medicare_fraud_cms_desynpuf.yaml`'s `policy_rules` (validated by `PolicyRulePack`/`PolicyRule` in config/schema.py, evaluated by Flow P); `demo-cms` wraps `build_tennessee_subset` + `demo_ingest_tn_subset.sh` behind readiness probes; the presenter script adapts `ui_reference_code/demo/presenter-script.md`'s 3-act structure to the REAL surfaces shipped in B1–B3/U2/alerts.36; the e2e spec follows the housing specs' reference-vs-live branching precedent.

**Tech Stack:** YAML config, bash, Markdown, Playwright/TypeScript. No backend code changes.

## Global Constraints

- **Configured, not coded**: the fraud patterns use ONLY the existing predicate model — single-field bounded comparison over `properties.<name>` | `risk_score` | `metric.<name>` with ops eq/neq/gt/gte/lt/lte/in/not_in and `config_ref` thresholds (config/schema.py:393-466). No new operators, no schema changes. The graph-derived fields B1 writes back onto entities (`active_alert_count`, `community_id`, `centrality_score`) and the risk composite are the legal signal surface.
- Demo claims in the presenter script must be TRUE of the running product on the 1% TN subset — no mockup numbers, no capabilities we don't have (no Timeline tab, no peer-comparison bars — both phase-2 per the U1 design §6). Where the reference script sells a feature we lack, the scene is adapted or cut, never faked.
- The e2e spec never `page.route`-mocks a subject under test; `/api/`-anchored patterns only for unavoidable auxiliary mocking. Live mode is data-gated (skips cleanly when no TN demo KB exists) so the default `make test-e2e` run stays green without bulk data.
- Shell follows `demo_ingest_tn_subset.sh`'s conventions (`set -euo pipefail`, `post_with_retry`-style resilience, `CHILI_API_URL` env default). Makefile target carries the `## description` help comment and a section banner per Makefile conventions.
- Gates: frontend `npm run test:run` + `npm run lint` + `npm run build` when e2e/TS files change; backend `pytest tests/config -q` + bare pyright + ruff when pack YAML changes; `backlog_consistency.py --check` after backlog edits. Commits end `(D1)`.
- Docker/live verification stays in the controller session (Task 5). Subagents never run docker or the demo itself.

#!/usr/bin/env bash
